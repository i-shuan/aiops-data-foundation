從 K8s 到 AIOps：原本的設計，與全進 Elasticsearch 的新方向

同一個 K8s cluster 裡住著好幾個部門的系統，目標是讓 IT 維運人員掌握程式與 server 健不健康，靠的是每個程式和每台 server 產生的數值、log、trace 三種資料。這頁把兩個做法放在一起比：原本各走各的三條路，以及討論中的「一套收集、全進 Elasticsearch、AIOps 自己訓練」。下面附廠區變多時的維運量與資料量試算。

先看懂三種資料

下面的架構圖一直出現三個詞：數值、log、trace。它們是同一個系統吐出來的三種不同的東西，各回答一個問題。用範例程式 demo-web 呼叫 demo-api、demo-api 變慢這件事當例子。

數值回答「有沒有出事、什麼時候開始」；log 回答「為什麼」；trace 回答「在哪裡」。三種要帶同一組標籤才串得起來。

監控的是什麼

目標是讓 IT 維運人員知道兩件事：程式健不健康、server 健不健康。他們最花時間的是找根因，所以 AIOps 最終要做到的是「出事時指出最可能的源頭」；要做到這件事，得先做異常偵測。

對象看什麼資料從哪來
程式健康度有沒有活著、重啟幾次、回應慢不慢、錯誤比例、處理量、用了多少 CPU 與記憶體程式自己吐的數值、容器的資源用量、程式的 log、trace
server 健康度CPU、記憶體、磁碟、網路、節點是不是正常節點上的收集程式、K8s 回報的節點狀態、系統 log
部門管什麼在這套裡對應
ICSDinfra，server 底層的監測server 健康度
TSIDMES、RMS、EAP 相關的程式程式健康度
BSIDERP 相關的程式程式健康度
IMCapp 應用先放著，這一輪不處理
platform整套 AIOps：收集程式、Elasticsearch、Kibana、訓練與偵測的程式這套系統自己的健康度

不在範圍內：機台收值，以及機台與製程本身有沒有異常（溫度、壓力、流量）。那是製程與設備工程師的需求，這裡不收、不存、不拿來訓練。

項目算法

不壓縮每秒筆數 × 86,400 × 每筆 bytes × 保留天數 × 份數
數值壓縮後最近幾天留原始；更舊的改成每幾分鐘一筆；出事的時段不管多舊都留原始
log 壓縮後只留指定的等級；出事的時段全留
trace 壓縮後出錯與太慢的全留；正常的抽樣；出事的時段全留
tokenbytes ÷ 每個 token 的 bytes。壓過的版本：數值用壓過的、log 用歸類後的、trace 只給出錯與太慢的

沒有算進去的：索引的額外開銷、實際的壓縮率、尖峰時段、以及壓縮本身要花的運算。實際數字會有出入。

預設值的來源：規模是常見的量級，不是你們環境量出來的。每筆佔用的 bytes、log 留下的比例、歸類後剩的比例、出事時段的比例，全部是我放的假設。其中「一筆原始數值佔幾 bytes」和「log 留下的等級佔百分之幾」對結果影響最大，要拿你們真的資料量過才準。

原本的架構

已經做完的：metrics 這一條

  • 系統不用知道資料送去哪各系統只在設定檔寫一個部門代號。要換部門，改那一行，程式不用動。
  • 加部門不用加線每個 cluster 往中央的線只跟站數有關：兩站就是兩條。新增部門是在對照表加一列。
  • 不能冒充別的部門程式自己宣稱的部門代號會被丟掉，只認 namespace 上掛的門牌。這一點實際測過。

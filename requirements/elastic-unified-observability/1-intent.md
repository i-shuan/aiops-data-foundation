# Intent — 程式與 server 健康度的 AIOps：三種資料全進 Elasticsearch

> 方向已確認（2026-10-05）。標 ❓ 的細節留到各個子需求的 spec 再定。
> 這是 branch `explore/elastic-all-in` 上的新方向，取代原本「metrics 寫 VictoriaMetrics」的做法。
> 原本那份需求已從這條 branch 刪掉，在 branch `chore/ai-native-scaffold`。

## 解決誰的什麼問題

IT 維運人員。值班時要知道兩件事：程式健不健康、server 健不健康。最花時間的是
**找根因**：告警一次響一堆，要靠人看儀表板、翻 log、憑經驗判斷哪個才是源頭。

要讓機器幫忙，三種資料（metrics、log、trace）得先對得起來。原本的設計是三套收集
程式、三座儲存，標籤各寫各的；廠區一多，每一套都要乘上廠數來維護。

## 監控的對象

只看這兩類。機台收值的資料不在範圍內。

| 對象 | 看什麼 | 資料從哪來 |
| --- | --- | --- |
| 程式健康度 | 有沒有活著、重啟幾次、回應慢不慢、錯誤比例、處理量、用了多少 CPU 與記憶體 | 程式自己吐的數值、容器的資源用量、程式的 log、trace |
| server 健康度 | CPU、記憶體、磁碟、網路、節點是不是 Ready | 節點上的收集程式、K8s 回報的節點狀態、系統 log |

### 部門各管什麼

| 部門 | 管什麼 | 在這套裡對應 |
| --- | --- | --- |
| ICSD | infra，server 底層 | server 健康度。資料標成 `icsd` |
| TSID | MES、RMS、EAP 相關的程式 | 程式健康度 |
| BSID | ERP 相關的程式 | 程式健康度 |
| IMC | app 應用 | 先放著，這一輪不處理 |
| platform | 整套 AIOps：收集程式、Elasticsearch、Kibana、訓練與偵測的程式 | 這套系統自己的健康度。資料標成 `platform` |

| 歸屬 | |
| --- | --- |
| 程式 | 屬於某個部門，照 namespace 的門牌貼標籤 |
| server | 歸 ICSD。server 不在任何 namespace 裡，沒有門牌可讀，由收集程式直接標成 `icsd` |
| AIOps 這套系統自己 | 歸 platform |
| 沒掛門牌、門牌寫錯的 | 也先歸 `platform`：不會消失、不會混進任何部門，由管這套系統的人去追是誰沒掛 |

## 不做會怎樣

| 現況 | 代價 |
| --- | --- |
| 三套收集程式、三座儲存 | 每多一個廠，要多顧的東西是三倍 |
| metrics 照 `tenant` 分、log 照 `dept` 分 | 同一個故障的數值和 log 對不起來 |
| trace 完全沒有 | 根因分析沒有資料可用 |
| 現成的異常偵測都在付費版 | 不付費就沒有 AIOps |
| 值班靠人看儀表板與翻 log | 找原因慢，而且只有少數人會 |

## 成功長什麼樣

本機 k3d 上，一個程式和它所在節點的健康度資料（metrics、log、trace），由同一個收集
程式送進同一座 Elasticsearch，帶著一樣的標籤；故意讓那個程式變慢或讓節點的資源吃緊，
自己訓練的偵測會把異常寫回去，在 Kibana 看得到是哪個程式、哪台 server。

## 已談定

| 項目 | 決定 |
| --- | --- |
| 儲存 | 三種都進 Elasticsearch。不用 VictoriaMetrics，不架 Tempo |
| 收集 | 一套收集程式收三種，標籤規則只寫一份。用 OpenTelemetry Collector |
| AIOps | 自己訓練。Elasticsearch 只當倉庫，不依賴它付費的機器學習功能 |
| AIOps 的目標 | 找根因。先做異常偵測，因為要先知道「哪裡不正常、什麼時候開始」才找得到源頭 |
| AIOps 看什麼、給誰用 | 程式健康度與 server 健康度，給 IT 維運人員用。見「監控的對象」 |
| 機台收值 | 不做。機台的量測值不收、不存、不拿來訓練 |
| 授權 | 以免費版能做到的為準 |
| Elasticsearch 幾座 | 先一座，用最新版。第二座在設定裡留位置，不啟用 |
| namespace 貼部門門牌的做法 | 沿用。`app/<app>/k8s/` 不用重做 |
| 範例程式 | 換一支跟機台無關的。見下面「範例程式」 |
| 資料不是全部留原始 | 分層保留，見下面「資料保留的原則」 |

## 範例程式

本機驗證要有東西可以監控、可以弄壞。原本跟機台有關的三支範例（`eqp-collector`、
`metrics-sim`、`yms-sim`）都已移除（2026-10-05）。repo 裡只剩 `mes-dispatch`。

新的範例程式要做到：

| 要求 | 為什麼 |
| --- | --- |
| 跟機台、製程無關，就是一支普通的服務 | 不讓人誤會這套在做機台收值 |
| 至少兩支互相呼叫（前面那支呼叫後面那支） | 找根因要有「源頭」和「被拖累的」才驗證得出來 |
| 自己會產生流量 | 不用另外打流量就有資料 |
| 可以從外面讓它變慢、出錯、吃資源 | 製造已知的故障，看偵測和找根因對不對 |
| 吐出三種資料，而且 log 帶著 trace 的編號 | 三種資料對得起來是整件事的地基 |

## 資料保留的原則

| 原則 | 做法 | 為什麼 |
| --- | --- | --- |
| 分層保留 | 數值：最近幾天留原始，更舊的壓成每幾分鐘一筆。log：只留指定的等級。trace：正常的抽樣 | 全部留原始的話，廠區一多磁碟撐不住 |
| 出事的時段全留 | 故障前後的三種資料不壓、不抽樣、不丟等級，不管多舊 | 那一段最有價值，查原因和驗證模型都要靠它 |
| 模型吃壓過的資料 | 訓練與偵測讀的是壓過的數值，不是原始的。學出來的「平常的樣子」每天更新，不每次重拉歷史 | 原始資料是給人查的。每次重訓都拉原始，對 Elasticsearch 的負擔太大 |
| 訓練時排除出事的時段 | 出事的時段不拿來學「平常的樣子」；越近的資料權重越高 | 不然模型會把故障學成正常 |

⚠️ 壓成一天一筆不夠用：異常通常只持續幾分鐘到幾十分鐘，日夜班的週期也會不見。

### 不壓縮與壓縮後的差別

下表全部是**假設值**算出來的，不是量出來的：2 個廠、每廠 2 個 cluster、每個 500 個 pod；
數值原始留 7 天後壓成 5 分鐘一筆，log 留 40%，正常的 trace 留 5%，出事的時段佔 1%。
完整的假設與算法在 [`architecture.html`](../architecture.html) 的試算，可以換成自己的數字。

| | 不壓縮 | 壓縮後 | 剩多少 |
| --- | --- | --- | --- |
| Metrics 要存 | 2.07 TB | 0.92 TB | 44% |
| Log 要存 | 4.84 TB | 1.96 TB | 41% |
| Trace 要存 | 1.69 TB | 0.13 TB | 8% |
| 三種合計要存 | 8.61 TB | 3.02 TB | 35% |
| 每次重訓要從 Elasticsearch 拉出 | 645 億筆 | 65 億筆 | 10% |
| 一次事件交給語言模型的 token | 1,710 萬 | 106 萬 | 6% |
| 一整天的資料全部交給語言模型的 token | 821 億 | 51 億 | 6% |

| 從這張表看出來的 | |
| --- | --- |
| 最大宗是 log | 不壓縮時佔一半以上。最該先定的是「log 留哪些等級」 |
| 壓得最多的是 trace | 因為正常的請求佔絕大多數，抽樣的效果最明顯 |
| 壓過之後一次事件仍然有上百萬 token | 超過語言模型一次讀得下的量。不能把資料直接丟給它，要先由偵測與關聯挑出最相關的再交出去 |
| 這些比例很依賴假設 | 尤其是「一筆數值佔幾 bytes」和「log 留下的比例」，要拿真的資料量過 |
| 不收機台的量測值之後 metrics 會更少 | 少多少要看它原本佔多大，上表沒有算進去 |

## 對這份需求的分析

方向沒有問題，但有六件事會決定做不做得成，寫在這裡免得之後才發現。

| # | 風險 | 影響 | 怎麼處理 |
| --- | --- | --- | --- |
| 1 | 找根因需要知道程式之間誰呼叫誰 | 這份資訊主要來自 trace，而 trace 要各部門在程式裡埋追蹤，平台單方面做不完 | 第 5 步先用不需要 trace 的線索：誰最早異常、是不是同一台 server、是不是同一個 namespace。有 trace 的程式再用呼叫關係加強 |
| 2 | 沒有過去出事的紀錄 | 自己訓練的模型無從驗證準不準 | 先靠範例程式製造已知的故障來驗證。正式上線前要開始累積事件紀錄 |
| 3 | 三種資料和 AIOps 全壓在同一座 Elasticsearch | 它出事時，監控、查詢、偵測一起停，而且沒有東西會告訴你 | 要有一個不依賴它的最小監控，只看它活著沒 |
| 4 | 原本測過的四件事要在另一套軟體重做 | 依門牌分部門、擋冒充、多個目的地、斷線補送都不能假設成立 | 第 1 步的驗收照原本需求 2、3 的標準，包含「故意改壞要被測到」 |
| 5 | 廠區變多時資料量等比例增加 | 磁碟與 Elasticsearch 的負載 | 保留原則已定。具體數字要拿真的資料量過，見 `architecture.html` 的試算 |
| 6 | 找根因的產出是「最可能的幾個候選與證據」，不是唯一的答案 | 期待太高會覺得沒用 | 驗收用「真正的源頭有沒有排在前三名」這類標準，不是「有沒有指出唯一答案」 |

⚠️ 第 1 項是最大的外部依賴。如果各部門不願意埋 trace，找根因能做到的精度會明顯
受限，這一點要先讓主管知道。

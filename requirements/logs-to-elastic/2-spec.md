# Spec — log 經同一套收集程式進 Elasticsearch

> `1-intent.md` 已確認（2026-10-06），四題都照建議。這一份要人確認之後，才寫 `3-plan.md`。
> 「行為」表的每一列都會變成 `4-acceptance.md` 的一條驗收項。

## 先實測過的

2026-10-06 在本機的 `obs-test` 上，用暫時的設定試了一次：節點那一份收集程式多讀容器的
log 檔，套跟數值同一組標籤規則，送進同一座 Elasticsearch。試完已換回正式的設定，repo 沒有動。

| 要確認的 | 實際結果 |
| --- | --- |
| 讀得到容器的 log | 讀得到。從檔案路徑就知道是哪個 namespace、哪個 pod、哪個容器 |
| 照部門分開 | 分得開。自動長出三份資料流，名字結尾是 `tsid`、`bsid`、`platform` |
| 標籤跟數值一樣 | 一樣。`tenant`、`dept`、`system`、`site`、`cluster` 都有，值跟同一個 pod 的數值相同 |
| JSON 的 log 拆成欄位 | 拆得開。`level`、`msg`、`trace_id`、`route`、`code` 各自是一個欄位，原文也留著 |
| 時間 | 用的是容器寫出那一行的時間，不是收集程式讀到的時間 |

| 試的時候發現的 | 說明 |
| --- | --- |
| 第一次啟動會把節點上現有的 log 全部讀進來 | 範例程式跑了 13 小時，一分鐘內進了 18 萬筆。見下面 ❓ 第 1 題 |
| 每支程式的欄位名稱不一樣 | 範例程式用 `level`、`msg`；Elasticsearch 自己用 `log.level`、`message`。不統一的話查「所有錯誤」要寫好幾種條件。見 ❓ 第 2 題 |
| 數字欄位進去變成小數 | `code` 是 200，存進去是 `200.0`。查得到，但要知道 |
| 還沒試的 | 不是 JSON 的 log、log 裡自稱別的部門、停機補送會不會重複、欄位型別衝突、容器重啟後換檔 |

## 資料怎麼走

```mermaid
flowchart LR
  P["每個容器印的 log"] --> F["節點上的 log 檔"]
  F --> C["節點那一份收集程式<br/>記住讀到哪、拆 JSON、<br/>讀門牌、擋冒充、補廠區"]
  C -->|"送不到先存磁碟"| E["Elasticsearch<br/>每個部門一份 log 的資料流"]
```

跟數值那一條的差別只有來源：數值是去抓，log 是讀節點上的檔。標籤規則與送出的設定共用。

## 收集程式

| 項目 | 內容 |
| --- | --- |
| 放在哪 | 節點那一份（`platform/otel/node-collector.yaml`），每個節點本來就有一個。不另外加收集程式 |
| 讀哪些 | 節點上所有容器的 log。收集程式自己的排除 |
| 讀到哪記在哪 | 跟佇列同一個地方：節點的磁碟。收集程式重啟後從上次讀到的地方繼續，不重讀也不跳過 |
| JSON 的 log | 拆成欄位，原文留著 |
| 不是 JSON 的 | 整行當訊息，照樣收 |
| 送到哪 | 同一座 Elasticsearch，資料流的名字是 `logs-<來源>-<部門>` |

## 標籤的規則

跟數值完全一樣，同一份規則：

| 資料 | `tenant` 怎麼來 |
| --- | --- |
| 有門牌的 namespace 裡的容器 | 照門牌 |
| 沒掛門牌，或值不在清單裡 | `platform` |
| 收集設定所在的 `obs`、系統元件的 `kube-system` | `platform` |

log 沒有「server 本身」這一類（節點的系統 log 這一步不收），所以不會有 `icsd` 的 log。

## 行為

| 情境 | 預期行為 |
| --- | --- |
| namespace 貼 `tenant: tsid` | 它的容器的 log 只出現在 `tsid` 那一份 |
| `tsid`、`bsid` 各一個 namespace | 各自只出現在自己那一份 |
| 沒貼、或貼成不在清單裡的值 | 進 `platform`，不會不見 |
| 每筆 log | 帶 `tenant`、`site`、`cluster`；門牌有的話帶 `dept`、`system`。值跟同一個 pod 的數值相同 |
| 每筆 log | 帶 namespace、pod、容器的名稱 |
| 一行 JSON 的 log | 等級、訊息、`trace_id` 各自查得到；原文也查得到 |
| 一行不是 JSON 的 log | 收得到，整行是訊息，不會被丟掉也不會讓後面的 log 卡住 |
| log 的 JSON 裡自己寫 `tenant`、`site`、`cluster` | 不算數。部門照門牌，這幾個自稱的欄位不留在資料上 |
| 把 `demo-api` 弄成一半回錯誤 | 查得到 `demo-api` 等級是錯誤的 log；拿其中一筆的 `trace_id` 去查，也查得到 `demo-web` 那一筆 |
| 收集程式自己的 log | 不收 |
| Elasticsearch 停機幾分鐘再恢復，中間重啟收集程式 | 停機期間的 log 補回來：筆數不少於程式實際印的 95%，也不多於 100%（不重複） |
| 收集程式平常重啟 | 重啟前後的 log 不重複、不漏 |
| 容器重啟 | 新舊兩個容器的 log 都收得到 |
| 兩支程式用同一個欄位名稱但型別不同 | 兩支的 log 都進得去。型別跟先到的不合的那個欄位查不到，原文查得到 |
| 數值那一條 | 不受影響：上一步的測試照樣全過 |

## 邊界與限制

* 輸入的合法範圍：容器印到標準輸出、標準錯誤的 log。一行一筆。
* 超出範圍時怎麼處理：跨好幾行的 log（錯誤堆疊）每行各自一筆，不合併。
* 程式直接寫到容器裡檔案的 log 不會被收。
* 資料量：這一步全收，不過濾等級。範例程式每個請求一行，兩組程式每秒約 8 行。
* 版本：跟上一步相同，Elasticsearch 9.5.3、OpenTelemetry Collector contrib 0.161.0。
* 授權：只用免費版有的功能。

## 影響到哪些既有行為

| 既有行為 | 會變成怎樣 | 需要改既有測試嗎 |
| --- | --- | --- |
| 節點那一份只收數值 | 多收 log。同一個程式、同一個佇列、同一顆磁碟 | `tests/obs/check.py` 加 log 的檢查 |
| 兩份收集設定的標籤規則要一字不差，`tests/validate.sh` 會比 | 規則要多一段給 log 用的。兩份都加，還是一字不差 | 要改：多查 log 那一段 |
| `tests/validate.sh` 擋「拿掉擋冒充」等改壞的寫法 | log 那一段也要有同樣的檢查與改壞的對照 | 要改 |
| 節點那一份的記憶體上限 384Mi | log 量大時可能不夠。這一步用範例程式的量驗，上限先不動 | 不用 |
| 佇列在節點的磁碟上，數值與 log 共用 | Elasticsearch 停很久時 log 會比數值先把佇列佔滿 | 不用。佇列滿了的行為這一步不測，列在「不涵蓋」 |
| 節點那一份唯讀掛載主機的 `/` | log 檔就在裡面，不用多掛 | 不用 |
| `platform/logging/fluent.conf` | 驗收過了就刪 | 不用，沒有測試用到它 |
| `tests/obs/run.sh outage` 比數值的抓取次數 | 多比 log 的筆數 | 要改 |

## 還沒談定的 ❓

| # | 問題 | 我的建議 |
| --- | --- | --- |
| 1 | 收集程式第一次到一個節點時，節點上已經有的舊 log 要不要讀 | 讀。不讀的話，收集程式晚於程式啟動的那一段 log 永遠補不回來。代價是第一次會有一波量，正式上線時要挑時間。之後重啟不會重讀，因為有記住讀到哪 |
| 2 | 欄位名稱要不要統一 | 只統一兩個：等級與訊息。`level` 或 `log.level` 都放進標準的等級欄位，`msg` 或 `message` 都放進標準的訊息欄位。其餘照程式自己取的名字。全部統一做不到，每支程式不一樣 |
| 3 | 兩支程式的同名欄位型別不同（一支的 `code` 是數字，另一支是文字） | 已實測（2026-10-06）：兩筆都進得去，log 不會掉。後到的那一筆裡，型別不合的那個欄位查不到，但原文還在。所以不另外處理，這個限制寫進文件 |
| 4 | `trace_id` 要不要放進標準的 trace 欄位 | 這一步不放，留在一般欄位，查得到就好。標準的欄位有格式要求，等第 4 步真的收 trace 時一起對齊 |

## 這份 spec 不涵蓋的

| 不涵蓋 | 為什麼 |
| --- | --- |
| trace 的收集 | 第 4 步 |
| 節點本身的系統 log | 見 `1-intent.md` |
| 過濾等級、把相似的 log 歸類、保留多久 | 總綱的分層保留，另外開 |
| 多行 log 的合併 | 已定不做 |
| 遮掉敏感內容 | 見 `1-intent.md` |
| 誰能看哪個部門的 log | 跟數值一樣，資料流分開、權限另外定 |
| 佇列滿了丟哪些資料 | 上一步也沒測。要另外開一個需求一起驗數值與 log |
| log 量很大時收集程式的資源用量 | 範例程式的量太小，驗不出來 |
| Kibana 的畫面 | 用查詢確認 |

# Intent — log 量大的時候不掉、不重複

> 這一份要人確認之後，才寫 `2-spec.md`。接在 [`logs-to-elastic`](../logs-to-elastic/1-intent.md) 之後，
> 補它「已知未涵蓋」裡的「log 量很大時收集程式夠不夠力」。

## 解決誰的什麼問題

要用 log 做異常偵測與找根因的人（之後的 AIOps）。出事的時候正好是 log 量暴增的時候，
如果那時掉了一段或重複了一段，模型看到的錯誤數就是錯的，而且沒有人會知道。

## 不做會怎樣

| 現況 | 代價 |
| --- | --- |
| 節點那一份收集程式只用範例程式的量驗過，每秒十行左右（見 [`platform/README.md`](../../platform/README.md)「還沒做、沒測的」） | 不知道每秒幾千行時會不會掉、會不會重複、會慢多少 |
| 寫入 Elasticsearch 設成一次只送一批（`num_consumers: 1`），這是為了停機時少掉資料 | 量大時一批一批送可能跟不上，佇列滿了以後的行為沒測過 |
| 用 Fluent Bit 做過同樣的測試（branch `claude/elasticsearch-log-pipeline` 的 `docs/elasticsearch-testing.md`），每秒約 4,800 行時抓到兩個問題，見下表 | 換了收集程式，這兩個問題在這邊會不會發生，不知道 |

用 Fluent Bit 測到的兩個問題：

| 問題 | 原因 | 這邊要確認的 |
| --- | --- | --- |
| 新 pod 開頭約 10 MB 的 log 整段不見 | kubelet 預設 log 檔滿 10 MB 就改名再壓縮，收集程式還沒讀到就被改名了 | `file_log` 只讀 `*.log`。改名成 `0.log.<時間>` 之後，沒讀完的那段還會不會讀 |
| 同一批寫了好幾次，而且一直重送 | 寫入成功了，但回應太大讀不完，被當成失敗重送 | 這邊的寫入程式在量大時會不會把成功的當失敗 |

## 成功長什麼樣

一個帶序號的 log 產生器，每秒 500、2,000、5,000 行各跑 2 分鐘，進到 Elasticsearch 之後：

| 檢查 | 預期 |
| --- | --- |
| 掉了幾行 | 0。依序號找得出掉的是哪幾號 |
| 重複幾行 | 0 |
| 從印出到查得到 | 每一段各記 p50、p99，寫進驗收結果 |
| 收集程式的 CPU、記憶體 | 每一段各記一次，跟目前的資源上限比 |
| 某一段做不到 0 掉、0 重複 | 找出原因：改設定修掉，或寫明能撐的上限與超過時會發生什麼 |

## 明確不做什麼

| 不做 | 為什麼 |
| --- | --- |
| 誰能看哪個部門的資料 | 這次先不做，另外開 |
| 連線逾時會掉資料的問題 | 已經寫在 `platform/README.md`，是另一個需求。這次只測 Elasticsearch 正常的時候 |
| 多個節點 | 本機只有一個節點 |
| 把 Elasticsearch 調快 | 中央那座的規格不在這個 repo。這次量的是收集程式這一側 |
| 等級的判斷、多行合併 | 跟量無關，另外開 |
| 只留某些等級、log 留多久 | 總綱的保留原則，另外開 |

## 會安靜壞掉的地方

| 症狀 | 原因 | 為什麼沒人會發現 |
| --- | --- | --- |
| 出事那段時間的 log 少了一截 | 量大時檔案被改名或佇列滿了，那段沒讀到或被丟掉 | 收集程式只印一行警告，Elasticsearch 這邊只是筆數少一點，不會報錯 |
| 錯誤數比實際多 | 同一批被寫了兩次 | 每一筆看起來都是正常的 log |

## 還沒談定的 ❓

| # | 問題 | 我的建議 |
| --- | --- | --- |
| 1 | 一個節點最多每秒幾行要撐得住 | 測到每秒 5,000 行。實際的尖峰量如果知道，用實際的數字 |
| 2 | 在哪裡跑 | 這次的環境跑不了 k3d，用本機的 k3s。`tests/obs/` 要加一個不靠 k3d 的跑法，會動到 `tests/`，寫進 `2-spec.md` |
| 3 | 如果一次只送一批跟不上 | 不直接改成多批同時送，那會讓停機時掉更多。先量出跟不上的點，再在 `2-spec.md` 比較做法 |

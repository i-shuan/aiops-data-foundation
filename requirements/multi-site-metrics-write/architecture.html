監控資料租戶分流
AIOPS DATA FOUNDATION ・ 2026-10-04 更新

各部門的監控資料，自動進到自己的租戶

同一個 K8s cluster 裡住著好幾個部門的系統。每個系統只要在自己的設定檔寫一個部門代號，它的監控資料就會被送進該部門專屬的資料空間，別的部門看不到。資料同時寫到中科、二林兩站，任何一站停機都不會掉。

資料怎麼走

流程圖載入中。如果一直沒有出現，下面的「實測結果」表格有同樣的資訊：四個部門的資料各進 1001 到 1004，沒掛門牌、寫錯和冒充的都進 1000。

這樣做的三個重點

  • 系統不用知道資料送去哪各系統只在設定檔寫一個部門代號。要換部門，改那一行，程式不用動。
  • 加部門不用加線每個 cluster 往中央的線只跟站數有關：兩站就是兩條。新增部門是在對照表加一列。
  • 不能冒充別的部門程式自己宣稱的部門代號會被丟掉，只認 namespace 上掛的門牌。這一點實際測過。

實測結果

在本機的測試環境把七種情況都實際部署一次，查每個租戶裡有沒有資料。軟體版本跟 AP1105 相同。

情況資料進了哪個租戶結果
門牌寫 tsid1001符合
門牌寫 bsid1002符合
門牌寫 icsd1003符合
門牌寫 imc1004符合
沒掛門牌1000符合
門牌寫錯字（imcc）1000符合
沒掛門牌，程式自稱 tsid1000擋下

也做了反向確認：故意把防冒充的規則拿掉，最後一種情況的資料就真的跑進 1001，測試會報錯。代表這條防線是有作用的，而且被拿掉時會被發現。

兩廠雙寫的實測

實際關掉其中一站的入口，中間再把 vmagent 重啟一次，然後恢復，比較兩站收到的筆數。

測了什麼結果
平常兩站收到的資料七種情況完全一樣，每筆都標著廠區符合
中科站停機時的二林站照常收，筆數不變符合
停機中重啟 vmagent排隊的資料還在，繼續累積符合
恢復後的中科站30 筆，二林站 30 筆補回來了
對照：不把暫存放磁碟15 筆，二林站 36 筆會掉資料

最後一列是故意拿掉磁碟暫存的對照組，用來確認「重啟不掉資料」靠的確實是那顆磁碟。

要注意的限制：中央只檢查通行證，不檢查資料上的租戶編號。部門之間的隔離是靠每個 cluster 上的 vmagent 設定維持的，所以那份設定的檢查與測試是必要的防線。目前的結果都來自本機測試環境，還沒有在正式環境執行。

# 後期要接 LLM 還是 MLOps

**定案：以 LLMOps 為主軸，借機器學習的紀律（版本、評測、回測、feedback 閉環），統計層繼續做偵測，不自己訓練模型、不微調 LLM。**

```
統計層（MAD、規則、跟兄弟比）  ← 每天「算」統計值，不是訓練模型
        ↓ 異常
根因分析（程式算）
        ↓ 報告
LLM（現成模型，不訓練、不微調）
        ↑
feedback → 記憶（RAG）、排除訓練時段、調門檻
```

- **統計層的「訓練」保留**：每天用 4 週資料算每個時段的中位數、MAD，幾秒跑完，不需要 MLOps 平台，但不能拿掉；大量、穩定、可重現的偵測 LLM 做不到。
- **不微調 LLM**：微調就回到「訓練模型」，要資料、版本、重訓。用記憶（RAG）＋prompt 就夠，換更好的模型也不用重做。
- **這條路的邊界**：機台、製程的多變量資料，或量大到 LLM 處理不起的分類（每天幾萬筆都要判斷），才重新考慮自己訓練模型；IT 服務的 AIOps 不會遇到。MLOps 留到接機台、製程（階段 2）時再評估，先問設備、製程部門有沒有現成的。

## 三個詞的差別

| 詞 | 是什麼 |
|---|---|
| **AIOps** | 目標：用資料和演算法幫運維發現問題、找原因 |
| **RCA（根因分析）** | AIOps 裡的一個步驟：出事後找是哪裡造成的 |
| **MLOps／LLMOps** | 一種做法：怎麼管機器學習模型／LLM（版本、上線、驗證、監控） |

**現在的 RCA 不是 MLOps**：[engine/configs/rca](../../engine/configs/rca/README.md) 全是程式算（排序取最慢的 trace、每段扣掉下游時間跟平常比、找錯誤源頭、log 樣式比對），沒有訓練任何模型。整條線只有 baseline 有「學」，而且只是統計。RCA 要是改用「拿歷史事故訓練模型學症狀 → 根因」才會需要 MLOps；這裡的方向是用 LLM 加強，不訓練。

LLM 和 MLOps 原本的比較如下（這是定案前的分析，結論見上）：

- **MLOps**：讓「抓異常」更準（偵測層），取代或加強現在的 MAD baseline。
- **LLM**：讓「看懂、處理異常」更快（解釋、互動層），接在根因分析之後。

## 比較

| | 接 LLM | 接 MLOps |
|---|---|---|
| 解決什麼 | 把異常和根因報告翻成人話、建議處置、用問的查資料、對照過去事故 | 抓得更準：多指標一起看、預測趨勢、log 異常分類、學哪些告警是誤報 |
| 放在哪一層 | `aiops-anomalies`、根因報告**之後** | 取代或加強**現在的 baseline、規則** |
| 吃什麼 | 整理好的結構化結果：異常、根因報告、log 樣式、runbook、事故紀錄 | 大量原始時序＋**標註**（哪次是真事故、哪個告警是誤報） |
| 要不要標註 | 不一定（摘要不用；比對過去事故要事故紀錄） | **一定要**；沒有標註只能做無監督，不一定贏 MAD |
| 多久有用 | 馬上（根因報告已經是結構化的） | 至少幾個月、要有足夠事故 |
| 要架什麼 | 模型（雲端 API 或廠內自架）、prompt、RAG、驗證用的歷史案例 | 特徵管線、模型版本（例如 MLflow）、重訓、上線、飄移監控、回饋收集 |
| 成本 | 每次呼叫的錢或 GPU；量小時便宜 | 基礎設施＋長期有人顧 |
| 主要風險 | 講錯（幻覺）、資料出廠 | 標註不夠、模型飄移、誤報變多沒人信 |
| 跟現在地基的關係 | 直接接根因報告，幾乎不用改 | 讀資料層沿用；baseline 要能換模型 |

## LLM 能不能取代機器學習

**取代不了「算」，但能取代「訓練一個模型來判斷」。**

偵測層不交給 LLM：

| 問題 | 說明 |
|---|---|
| 量太大 | 約 1 萬條序列（服務 × API × 指標＋Pod）× 每 30 秒～5 分鐘 ＝ 一天幾百萬到幾千萬次判斷；MAD 一次幾毫秒 CPU，LLM 撐不住 |
| 算數字不可靠 | 中位數、百分位、z 值會算錯或「差不多」，最後還是要程式算 |
| 不一致 | 同一份資料問兩次結果可能不同；告警要能重現 |
| 講不出門檻 | MAD 能說「z=11，超過 5」，能調靈敏度、能稽核；LLM 只能說「偏高」 |
| 歷史太長 | baseline 用 4 週 × 168 個時段，塞進 prompt 太長太貴；先壓成摘要就等於先跑統計 |
| 資料出廠 | 每 30 秒把全部 metrics 送雲端，資安通常不過 |

統計層把量篩小之後，LLM 能接手的：

| 原本要 MLOps 做的 | LLM 取代？ | 原因 |
|---|---|---|
| 從原始時序抓異常、多指標異常模型 | ❌ | 見上表 |
| 趨勢預測（幾天後滿） | ⚠️ 不用 LLM，也不用自己訓練 | 簡單斜率就夠；要更準用現成的時序基礎模型（例如 Chronos、TimesFM），不是聊天型 LLM，廠內 CPU 或小 GPU 就能跑 |
| **誤報過濾** | ✅ | 一天只有幾十筆異常；看異常＋根因報告＋部署紀錄就能判斷，不用累積幾個月標註訓練分類器 |
| **新 log 樣式嚴不嚴重** | ✅ | 歸類後一天新增幾十種；懂語意（`Connection refused` vs `cache miss`） |
| **合併告警** | ✅ | 給它呼叫關係圖和異常清單判斷是不是同一件事，比寫一堆規則容易 |
| 根因推理、處置建議 | ✅ | 本來就不是傳統機器學習擅長的 |

## 分工

```
約 1 萬條序列，每 30 秒～5 分鐘
   │  統計層：MAD、規則、跟兄弟比（便宜、穩定、可重現）
   ▼
一天幾十筆異常
   │  根因分析（程式算：哪一段、錯誤源頭、log 樣式）
   ▼
幾件事故的結構化報告
   │  LLM：合併、判斷真假、解釋、建議、對照過去事故
   ▼
值班的人
```

- **讓 LLM 叫工具，不要自己算**：給它「查某服務的 trace」「算某段時間的 p95」之類的函式，數字由程式算，LLM 決定查什麼、怎麼解讀。
- **先用歷史事故驗證**：至少 20～30 件，確認判斷真假的準確率，才讓它過濾告警。
- **廠內或雲端**：誤報過濾、摘要的量，廠內自架的中型模型就夠；複雜推理才需要更強的模型。

## MLOps 要不要做

| MLOps 擅長的 | IT 服務需要嗎 | 原因 |
|---|---|---|
| 多指標異常模型（autoencoder、isolation forest…） | 暫時不用 | IT 服務的問題多半單一指標就看得出（錯誤率、延遲、重啟），MAD＋規則＋跟兄弟比已涵蓋大部分；抓到的「微妙異常」值班也不知道怎麼處理 |
| 趨勢、容量預測 | 不用自己做 | 斜率就夠，或用現成的時序基礎模型 |
| 誤報過濾、告警分類 | 不用 | 量小，LLM 接手 |
| log 異常偵測 | 不用 | log 樣式歸類（已有）＋LLM 判斷嚴重度 |
| **機台、製程的多變量模型**（預測保養、FDC、虛擬量測、良率） | **可能需要** | 感測器量大、變數多、有物理規律，又有明確結果（壞了沒、良率）可當標註，是機器學習最拿手的 |

不做的代價很小：現在的 baseline 本身就是輕量版（每天重訓、每個時段的參數存起來、偵測時讀出來）；要換模型時讓 baseline 那層能插拔就好，資料地基不動。MLOps 的成本是長期的（特徵管線、版本、重訓、飄移監控、要有人一直顧），沒有明確收益前不背。

**什麼時候再啟動（任一成立）：**

1. MAD 跑了幾個月，誤報或漏報仍明顯，而且原因是「要好幾個指標一起看」。
2. 範圍擴大到機台、製程（[factory-later.md](../factory-later.md)），而且有明確目標（減少非計畫停機、提早發現製程飄移）。
3. 已累積足夠標註：事故紀錄、告警回饋、機台的故障與保養紀錄。

> 公司若已有設備、製程部門在做 FDC、預測保養，那是他們的領域（感測器資料不一定經過這裡的 OTel）。比較好的分工是這個平台提供 IT 層資料（EAP 通訊、交握耗時、主機狀態）給他們的模型用，不從零自建一套 MLOps。

## feedback 閉環

加上 feedback 回寫，整條線就是會學習的閉環。要的是 **MLOps 的紀律，不是 MLOps 平台**。

**feedback 的四種用法（只做 1～3）：**

| # | 用法 | 例子 | 有沒有訓練 |
|---|---|---|---|
| 1 | 調參數 | 這條序列一直誤報 → z 從 5 調到 7，或提高 `min_abs` | 沒有，改設定 |
| 2 | 清訓練資料 | 10/3 是事故 → 訓練時排除；月底批次是正常 → 標成特殊時段另外學 | 影響 baseline 的統計值 |
| 3 | 寫進 LLM 記憶 | 「這種告警上次是誤報，原因是每月對帳批次」 | 沒有，是檢索 |
| 4 | ~~訓練分類模型~~ | 用累積的真／誤報訓練模型過濾告警 | **不做**，由 LLM＋第 3 項取代 |

**一定要有的四個紀律：**

| 風險 | 要做的 |
|---|---|
| 改壞了不知道（誤報調掉了，真的事故也沒報） | 每個告警記下是哪一版 baseline、哪一版設定、哪一版 prompt 產生的 |
| 改了退不回來 | 設定、標註、prompt、記憶都有版本，可以退回 |
| 沒驗證就上線 | **回測**（新門檻重跑過去 4 週）、**評測集**（20～30 件過去事故），通過才套用 |
| 回饋被污染（值班半夜把告警全按誤報） | 回饋不直接生效：要累積多次或第二個人確認；確認過的事故紀錄優先於單次回饋 |

規模是「幾個 index（`aiops-feedback`、`aiops-incidents`，baseline 帶 `version`）＋一支回測指令」，不需要 MLflow、Kubeflow、特徵平台。

**現況（程式裡查過）**：baseline 只記 `trained_at` 和訓練的時間範圍，沒有版本號；訓練時不排除事故時段（中位數不容易被帶偏，但事故拉長或剛好落在同一時段還是會被學進去）；沒有誤報回饋、逐條靜音或門檻調整；沒有回測。

## LLMOps 要管什麼

| MLOps 的觀念 | LLMOps 對應的 | 這裡要做的 |
|---|---|---|
| 模型版本 | 模型版本＋prompt 版本 | 固定模型版本；prompt 放 git，每次呼叫記下哪一版 |
| 訓練資料、標註 | 記憶、RAG 資料（事故、回饋、runbook） | 每筆有來源、時間、誰確認；能刪、能標過期 |
| 上線前驗證 | 評測集 | 過去事故讓 LLM 判斷，改 prompt 或換模型前都跑 |
| 監控變不準 | 準確率、成本、延遲、講錯話 | 每次呼叫記輸入、輸出、token、時間，對照之後的回饋 |
| 重訓 | **不用**：改 prompt、改記憶立刻生效 | 回饋寫進去就有效，刪掉就退回 |

**記憶的風險：**

| 風險 | 對策 |
|---|---|
| 被污染（誤按誤報，之後同類事故都放過） | 分等級：確認過的事故優先；單次回饋要累積多次才算 |
| 過期（舊版批次造成的誤報，改版後不成立） | 有期限或綁版本，過期降權或淘汰 |
| 互相矛盾 | 一起拿出來讓 LLM 說明差異；太多就交給人 |
| 抓錯記憶 | 評測集放「看起來像、其實不一樣」的案例 |
| **LLM 自己決定不報** | 先只**加註**（「可能是誤報，理由…」）；準確率夠了才讓它**降級**；永遠不讓它刪告警，統計層照常報 |

**用現有地基記錄 LLM 呼叫**：OpenTelemetry 有生成式 AI 的欄位標準（還在發展中），LLM 呼叫可以記成 trace 進同一個 ES，成本、延遲、錯誤沿用現有 baseline 監控，不另架平台。要現成介面（prompt 管理、評測、看每次呼叫）可以用能自架的開源工具（例如 Langfuse），適合資料不能出廠。

## 成功度與業界趨勢

沒有可信的業界數字能直接比「誰成功率高」；以這裡的情況（工廠 IT 服務的 AIOps、團隊不大、統計層已有）判斷：

| 範圍 | 成功機會較高 | 原因 |
|---|---|---|
| IT 服務的 AIOps（現在） | **LLMOps**＋統計層 | 不用標註、幾週見效、只要會 prompt 和工具函式；錯了有統計層兜底；能用文字說明理由；改壞立刻退回 |
| 機台、製程（階段 2） | **MLOps** | 有天然標註（壞了沒、良率）、數值型資料、業務指標明確 |

LLMOps 常見的失敗與對策：沒評測集就上線（講錯幾次就沒人信）→ 先用過去事故驗證；讓 LLM 自己決定 → 只加註、降級；丟一團原始資料 → 只給根因分析整理好的結果，要更多再叫工具查；資安擋下 → 一開始就規劃廠內自架；成本失控 → 只處理統計層篩出的異常、監控 token。

**先定怎麼量成功**，上線前記下現況當基準：每天告警幾筆、多少是誤報、從告警到找到原因平均多久。

業界趨勢（截至 2026 年中的認知）：話題已轉到 LLMOps（再往 AI agent 的維運延伸），MLOps 沒消失，而是成熟、不再被炒作，主要平台都把 LLM 的追蹤、評測加進來，兩者在合流。分工大致是**數值預測用傳統 ML，理解與推理用 LLM**。監控廠商（Elastic、Datadog、Dynatrace 等）的 AIOps 做法一致：底層統計／傳統 ML 偵測，上層 LLM 助理解讀告警、找根因，和這裡的架構相同。工廠的機台、製程、AOI 瑕疵檢測仍以 MLOps 為主。

## 兩邊共同的前提（都還沒做）

1. **事故紀錄**：時間、影響、根因、處置。LLM 的 RAG 要用，MLOps 的標註也要用。
2. **告警回饋**：值班按「真的」或「誤報」。MLOps 最重要的資料，也拿來驗證 LLM。
3. **告警出口與合併**：結果先送到人手上，才會有回饋。

## 路線

```
現在      統計層（MAD、規則、跟兄弟比）正式排程上線
          ＋ 告警出口、事故紀錄、回饋（先只收集，不自動生效）
          ＋ 訓練排除事故時段、baseline 與設定帶版本、回測指令
   ↓
接著      LLM：從「根因報告 → 摘要、處置建議」開始（只加註）
          評測集、prompt 版本、呼叫記錄；再做合併、判斷真假、讀事故與回饋記憶
          回饋累積夠且回測通過，才自動調門檻
   ↓
階段 2    接 EAP、機台 → 這時再評估 MLOps（先問設備、製程部門）
```

# 保留天數與容量（方案）

一句話：**原始資料只留查問題需要的天數；AIOps 學「平常的樣子」需要的長期資料，用降解析度的 metrics 和統計值留，便宜很多。**

⚠️ 這份是**方案，還沒套用**。數字確認後再改 ILM。

## 現況（實測）

| 資料 | 現在的保留設定 | 問題 |
|---|---|---|
| log（`k8s-*`） | 我們的 ILM `k8s-logs`：每天或 30GB 換一個 index，**30 天刪** | 異常偵測要至少 4 週的歷史，30 天剛好不夠看出完整的月週期 |
| metrics（`metrics-*.otel-*`） | ES 預設 ILM `metrics`：**只有 rollover，沒有刪除** | **永遠不刪，硬碟遲早滿** |
| trace（`traces-*.otel-*`） | ES 預設 ILM `traces@lifecycle`：**只有 rollover，沒有刪除** | 同上 |

## 每筆資料佔多少（測試環境實測）

| 資料 | 實測每筆 | 估算用 | 一筆是什麼 |
|---|---|---|---|
| log | 135 bytes | **250 bytes** | 一行 log。測試資料每行很像，壓縮特別好；真實 log 內容較雜，保守用 250 |
| Pod 資源（kubelet） | 57 bytes | 60 bytes | 一個 Pod 或容器的一組數值，每個 Pod 每分鐘約 13 筆 |
| K8s 物件狀態 | 47 bytes | 50 bytes | 每個 Pod 每分鐘約 5 筆 |
| 應用自己的 metrics | 78 bytes | 80 bytes | 一組維度的一個時間點。Java agent 預設會吐 JVM、HTTP 等幾十到上百組，**每個 Pod 每分鐘約 100～300 筆，要用真的 Java 服務量過** |
| trace | 276 bytes | **400 bytes** | 一段（span）。測試的 span 很簡單；真實的帶 HTTP、SQL 等欄位，保守用 400 |

都是 ES 壓縮後、**不含副本**的大小。正式環境有一份副本的話，**乘以 2**。

## 方案

### 原則

1. **原始資料留「查問題」需要的天數**：出事時要看到每一行 log、每一個 span、每 30 秒的數值，通常最近 1～4 週就夠。
2. **AIOps 的長期資料用「降解析度」和「統計值」**：學「平常的樣子」需要的是每 5 分鐘或每小時的數值，不需要每一行原始資料。
3. **至少留 13 個月的統計**：看得到年度的週期（年度保養、旺季、月底）。

### 建議的天數

| 資料 | 原始 | 降解析度後 | 刪除 |
|---|---|---|---|
| **metrics** | 30 秒一點，留 **14 天** | 第 14 天起降成 **5 分鐘一點**；第 90 天起降成 **1 小時一點** | **400 天**（約 13 個月） |
| **log** | 原文留 **30 天**（現在的設定） | 每 5 分鐘統計一次「每個服務各 level 的筆數、各 `error.type` 的筆數」，存成另一個小 index（ES 內建的 transform，免費），留 **400 天** | 原文 30 天 |
| **trace** | 原始 span 留 **7 天** | 每個服務、每個 API 的請求數、錯誤數、延遲分布，由 Collector 在收的時候算好（`spanmetrics`），當成 metrics 存，跟著 metrics 的規則降解析度、留 **400 天** | 原始 7 天 |
| failure store（ES 拒收的資料） | 留 **30 天**，夠查原因 | — | 30 天 |

**為什麼這樣分：**

- **metrics 降解析度**：實測免費授權可用。每小時一點只保留那一小時的最小、最大、總和、筆數，學「平常的樣子」夠用；一小時一點的大小約是原始的 1/120。
- **log 不留更久，改留統計**：log 原文是最佔空間的。AIOps 看 log 主要是「哪種錯誤突然變多」，留每 5 分鐘的筆數就夠，原文 30 天用來查細節。
- **trace 原文只留 7 天**：trace 主要用來查「最近這次出事」。長期要的是每個 API 的延遲、錯誤率，用 `spanmetrics` 在 Collector 算，**還有一個好處：它在取樣之前算，就算 trace 只記一成，請求數和延遲還是準的**。

### 容量估算

公式：

```
每天 = 每秒筆數 × 86,400 × 每筆大小 × （有副本就 × 2）
```

**以每 1,000 行 log／秒、500 個 Pod、每秒 500 個 span 估算（含一份副本）：**

| 資料 | 原始 | 降解析度、統計 | 合計 |
|---|---|---|---|
| log：1,000 行／秒 × 250 bytes | 每天 43GB × 30 天 = **1.3TB** | 統計值很小，約幾 GB | **約 1.3TB** |
| Pod 資源與 K8s 狀態：500 Pod × 18 筆／分 × 55 bytes | 每天 1.4GB × 14 天 = 20GB | 5 分鐘：76 天約 10GB；1 小時：310 天約 3GB | **約 33GB** |
| 應用 metrics：500 Pod × 200 筆／分 × 80 bytes | 每天 23GB × 14 天 = 320GB | 5 分鐘：76 天約 175GB；1 小時：310 天約 60GB | **約 560GB** |
| trace：500 span／秒 × 400 bytes | 每天 35GB × 7 天 = **245GB** | span metrics 併在 metrics 裡，很小 | **約 245GB** |
| **合計** | | | **約 2.1TB** |

**最吃空間的是 log 原文和應用自己的 metrics**。這兩個的量差異很大，要用正式環境的實際數字重算（見下一節）。

**ES 硬碟要再留 15%～20% 的空間**：ES 預設硬碟用到 85% 就不再放新的 shard、95% 就整個唯讀，所以實際要準備的硬碟是上表的 1.2～1.3 倍。

### 怎麼量正式環境的量

在正式的 ES 上查前一天每種資料各進來多少：

```
GET k8s-*,metrics-*.otel-*,traces-*.otel-*/_search
{"size": 0,
 "query": {"range": {"@timestamp": {"gte": "now-1d/d", "lt": "now/d"}}},
 "aggs": {"stream": {"terms": {"field": "data_stream.dataset", "size": 50}}}}
```

以及每個 index 的實際大小：

```
GET _cat/indices/.ds-k8s-*,.ds-metrics-*,.ds-traces-*?v&h=index,creation.date.string,docs.count,pri.store.size&s=creation.date
```

用這兩個數字乘上面的天數，就是正式環境要的容量。

## 要做的事（確認方案後）

1. **metrics**：自己的 ILM（hot → 14 天降成 5 分鐘 → 90 天降成 1 小時 → 400 天刪），掛在 `metrics-otel@custom`。
2. **trace**：自己的 ILM（7 天刪），掛在 `traces-otel@custom`。
3. **log**：`k8s-logs` 維持 30 天；新增一個 transform，每 5 分鐘把「服務 × level × `error.type`」的筆數寫進 `aiops-log-stats-*`，留 400 天。
4. **trace 的長期指標**：Collector 加 `spanmetrics`，從 trace 算每個服務、每個 API 的請求數、錯誤數、延遲分布，當成 metrics 送出。
5. **failure store**：設 30 天保留。
6. 用測試環境驗證：降解析度後的資料查得到、ILM 照時間推進（測試時把天數縮短成分鐘）。

## 要你決定的

1. **天數**：上面的 14 天／90 天／400 天、log 30 天、trace 7 天可以嗎？各部門（group）要不要不同？（index 本來就依 group 分開，可以各自設。）
2. **副本**：正式環境的 ES 要不要每份資料都有一份副本（容量 × 2）？三個節點以上建議要。
3. **正式環境的量**：用上一節的查詢查一次，我再用實際數字重算容量。

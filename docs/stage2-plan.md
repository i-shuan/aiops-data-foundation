# 落地五階段：階段一現況、階段二規劃

AIOps 落地常分五階段：**一、可觀測性基建 → 二、資料清洗與上下文打標 → 三、規則與 baseline → 四、根因分析 → 五、自動修復與回饋**。最耗時的通常是階段二（跨系統串接、統一 ID、清掉雜訊），主要是跨團隊協商，不是技術問題。

> 這是依**工作類型**分（基建 → 串接打標 → 判斷 → 根因 → 修復）。另一種分法是依**範圍**：先一般服務、再工廠（見 [factory-later.md](factory-later.md)）。

**範圍：只有一般服務**（Web API、worker、Kafka、DB）。工廠（EAP、機台、MES／MCS／AMHS、批號載具）之後再做，集中在 [factory-later.md](factory-later.md)。

**結論**：

- 階段一大致完成，只剩幾個小尾巴。
- 階段二只做了「身分、時間、HTTP 串接」這層。本文件規劃五項：時間對齊、Kafka 串接、業務 ID、髒資料排除、雜訊壓制。

### 2-1 時間對齊

**為什麼**：根因分析靠「誰先開始變壞」排順序，trace 靠呼叫方和被呼叫方的時間算延遲。主機時鐘差 1 秒，順序就可能顛倒、延遲變負的。

**現況**：

- ✅ 全部存 UTC。
- ✅ trace 有「時鐘不同步」規則：呼叫方和被呼叫方的時間差超過 500ms 就記（`trace.clock_skew_ms`）。
- ❌ K8s 節點、DB 主機的 NTP 狀態沒監控（EAP 主機見 [factory-later.md](factory-later.md)）。
- ❌ 「事件時間」和「進到 ES 的時間」差多久沒監控（Collector 卡住、ES 慢，看起來會像流量掉）。
- ❓ 沒帶時區的 log 時間（純文字 log 常見）怎麼解讀，要確認中央 pipeline 的預設。

**做法**：

| 步驟 | 內容 | 驗收 |
|---|---|---|
| 1. 主機時鐘監控 | K8s 節點：node_exporter 的時間偏移指標（`node_timex_offset_seconds`）；DB 主機同樣；加規則：偏移 > 100ms warning、> 1s critical | 每台主機都有偏移值，故意調偏一台會報 |
| 2. 收資料延遲 | log 記「事件時間」和「Collector 收到的時間」，算延遲分佈；延遲 > 1 分鐘報 warning | 停掉 ES 一段時間再恢復，延遲規則會報、恢復後消失 |
| 3. 時區規範 | 所有系統寫 UTC 或帶時區的 ISO 8601；沒帶時區的 log 一律依「主機所在地時區」解讀，並在文件寫清楚 | 規範寫進應用標準 |
| 4. 時鐘差日報 | 每天列出 trace 時鐘差最大的前 10 對服務 | 有日報 |

### 2-2 Kafka 串接

**為什麼**：請求進 Kafka 後，消費者那邊處理的 DB、呼叫要能接回原本的請求，不然根因分析在 Kafka 這裡就斷了。

**現況**（[aiops-trace.md 場景四](aiops-trace.md#四非同步訊息佇列)）：

- ✅ 排隊時間、消費落後（kafka_exporter）抓得到。
- ✅ 消費端的 `receive` span 有 link 指回生產端的 `publish`。
- ❌ **.NET 不改程式時，消費者處理訊息時的 DB、呼叫自成一個 trace**（k3s 實測 961／961 筆都是孤兒），接不回訊息。
- ❓ Java agent 理論上會自動帶 header、自動串起來，還沒在 k3s 驗證。

**做法**（三條路，可並行）：

| 路線 | 內容 | 代價 | 建議 |
|---|---|---|---|
| A. 驗證 Java | k3s 加 Java 的生產者、消費者，確認不改程式就能串起來 | 我們，1～2 天 | 先做：確認問題範圍是不是只有 .NET |
| B. .NET 加幾行 | 消費者收到訊息時，從 header 取出 trace context 當成處理時的上層（約 5 行） | 各應用團隊改程式 | 只對**重要的**消費者（工單、批號流轉）要求；之前決定先不改，這裡列為「之後談」 |
| C. 業務 ID 事後關聯 | 訊息的 key 或內容帶交易 ID、單號，生產端和消費端的 log 都記這個 ID，用 ID 接起來 | 依賴 2-3 | 不改程式時的退路 |

**驗收**：有 trace 能從 HTTP 入口一路看到消費者處理時查的 DB（路線 A／B）；或給一個交易 ID 能列出生產、消費兩邊的 log（路線 C）。

### 2-3 業務 ID（服務層）

**為什麼**：trace 斷掉的地方（Kafka 不改程式、批次工作、排程、呼叫外部系統），只能靠業務上的 ID 接起來；根因報告也要能說「影響了哪些交易、哪些單」。

**現況**：

- ✅ 工廠用的欄位已定案：`lot.id`、`equipment.id`、`work_order.id`、`recipe.id`（[apps/standards/tracing.md](../apps/standards/tracing.md)）。工廠的其餘欄位、MES／MCS／AMHS 斷鏈見 [factory-later.md](factory-later.md)。
- ❌ 服務層通用的「交易 ID」（一次操作從頭到尾的 ID，跨同步、非同步）還沒定名稱。
- ❌ 很多 ID 只寫在 log 訊息裡，沒有獨立欄位。

**做法**：

| 步驟 | 內容 | 誰 | 驗收 |
|---|---|---|---|
| 1. 訂名稱 | 服務層通用的交易 ID 欄位名稱（例如 `txn.id`），跟已定案的 `work_order.id` 等並列；新增要先跟平台確認 | 我們 | 寫進 [tracing.md](../apps/standards/tracing.md) |
| 2. 不改程式：從 log 抽出來 | 中央 pipeline 依格式把 `txnId=…`、`orderNo: …` 抽成標準欄位；舊系統只要 log 裡有寫就行 | 我們（要幾行 log 樣本） | 舊服務的 log 查得到 `txn.id` |
| 3. 新程式：放 MDC／scope、span 屬性 | 入口把 ID 放進 log 的 MDC（Java）或 scope（.NET），重要的也放成 span 屬性 | 各應用團隊（寫進開發規範） | 新服務的 log、trace 都帶 |
| 4. 查詢工具 | 給一個交易 ID，列出所有服務的 log、trace，依時間排序 | 我們 | 輸入一個 ID 看得到完整時間線 |
| 5. 根因報告帶 ID | 報告列出受影響的交易、單號 | 我們 | 報告裡有「影響哪些交易」 |

**一定要注意**：業務 ID **只放 log、trace，不放 metrics**（每個不同的值就是一條新序列，序列數會爆炸）。

### 2-4 髒資料排除

**為什麼**：系統天天噴的錯（被 catch 吞掉、沒人修），會讓 baseline 學成「每天報錯 1,000 次是常態」，真的出事反而抓不到；事故、歲修期間的資料學進去，也會把「平常」帶偏。

**現況**：

- ✅ 偵測得到：吞掉的例外、N+1、新出現的 log 樣式。
- ✅ baseline 用中位數＋MAD，少數幾次事故影響不大。
- ❌ 訓練時不會排除事故、歲修時段。
- ❌ 沒有「慢性病」清單。
- ❌ 沒有資料品質檢查（突然多出大量序列、某個欄位突然空掉）。

**做法**：

| 步驟 | 內容 | 驗收 |
|---|---|---|
| 1. 排除事故時段 | 確認過的事故（`aiops-incidents`，見 [system-map.md 第 10 節](system-map.md)）在訓練時排除；事故紀錄還沒有之前，先用「anomaly 連續超過 30 分鐘」的時段當候選、人工確認 | 插入一段事故再訓練，baseline 不被拉偏 |
| 2. 行事曆 | 國定假日、系統維護、大型活動：那段時間不判斷，也不學進去；年度特殊日可用去年同期（要先有 13 個月資料）。工廠的歲修、盤點見 [factory-later.md](factory-later.md) | 行事曆上的時段不報、不學 |
| 3. 慢性病清單 | 每週列出「天天噴錯、沒人修」的前 10 名：吞掉的例外、固定出現的 error log 樣式、一直被限流的容器，附服務負責人 | 每週有清單；修掉的從清單消失 |
| 4. 已知問題可以先靜音 | 慢性病還沒修好前，用 `tune` 調高那條序列的門檻或固定粒度，記下原因和期限（到期要重看） | 每筆都有原因、負責人、到期日 |
| 5. 資料品質檢查 | 序列數突然暴增（例如路由沒參數化：`/lots/A123` 每個批號一條）、必填欄位（服務名、trace.id）缺很多、某服務的資料突然停了 | 故意送沒參數化的路由會報 |
| 6. 排除測試流量 | 壓測、loadgen、測試 namespace 用 label 標出來，不學、不判斷 | 壓測期間不誤報 |

### 2-5 雜訊壓制

**為什麼**：一次 DB 變慢，同時會有好幾個 API 的延遲、錯誤率、連線池規則、跟兄弟比……30 分鐘上百筆。不收斂，值班的人很快就不看了。

**現況**：

- ✅ 跳一次 warning、連續兩個時間窗才 anomaly。
- ✅ 規則用 `for` 要持續一段時間；critical 規則一次就算。
- ✅ 依事件數自己選粒度（量少的不用 30 秒）、`min_abs`。
- ✅ 借來的 baseline 門檻較高。
- ❌ 還沒合併成同一件事故、沒有靜音、沒有發送頻率限制。

**做法**（四層收斂，[system-map.md 第 7 節](system-map.md)）：

| 步驟 | 內容 | 驗收 |
|---|---|---|
| 1. 同一條序列連續的點 → 一段 | 一段異常一筆：記開始、升級成 anomaly、結束的時間；恢復要連續 N 個時間窗正常（避免在門檻邊緣反覆開關） | 一段 10 分鐘的異常只有一筆，不是 20 筆 |
| 2. 同一個服務、時間重疊 → 一件 | p95＋錯誤率＋連線池規則＋跟兄弟比 → 一件事故 | 一次 DB 變慢只有一件 |
| 3. 沿呼叫關係 → 找源頭 | 上下游同時異常的合成一件，最下游、最早開始的當源頭候選（需要常駐拓撲：每天從 trace 算一次「誰呼叫誰」存下來） | 上下游一起慢時，源頭指到最下游 |
| 4. 排優先、靜音、限頻 | critical > 影響多個服務 > 可信度高 > 持續久；行事曆時段靜音；同一件事故通知後 N 分鐘內不重發 | 每天通知數、每件事故的異常數有統計 |

**衡量**：上線前先記下現況（每天幾筆異常、多少是誤報），之後看「每天通知幾件」「一件包含幾筆異常」「誤報率」有沒有下降。

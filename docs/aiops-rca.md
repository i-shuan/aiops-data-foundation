# AIOps：根因分析怎麼做、哪裡需要 AI

一句話：**根因分析不是每一步都需要 AI。真正需要 AI 的是「找出不正常」和「從大量候選裡排出最可能的原因」；中間串資料的步驟，用查詢和規則就做得到。**

這份說明這個 repo 收進 ES 的 log、metrics、trace 要怎麼用來做根因分析，以及最關鍵的一件事：**怎麼知道「平常的樣子」**。

## 三種資料各回答什麼

| | 回答的問題 | 例子 |
|---|---|---|
| metrics | **有沒有出事、什麼時候開始** | 「mes-api 的回應時間從 10:05 開始變慢」 |
| trace | **一個請求經過哪些服務、哪一段造成的** | 「慢在 wip-worker 查 Oracle 那一段，從 30 毫秒變 3 秒」 |
| log | **那一段裡面發生了什麼事** | 「wip-worker 10:03 起出現 full table scan on LOT_HISTORY」 |

三種都用同一套欄位（`service.name`、`service.version`、namespace、Pod、`group`／`dept`），log 的 `trace.id` 對得到 trace 的 `trace_id`，所以串得起來。

## 根因分析的六步

| 步驟 | 要回答的問題 | 用什麼做 | 需不需要 AI |
|---|---|---|---|
| **1. 發現異常** | 哪裡不正常？ | 每個服務、每個時段學出「平常的樣子」，偏離就標出來（見下一節） | ✅ **需要**。固定門檻在幾百個服務上不可行：每個服務的正常值不同，白天晚上也不同 |
| **2. 合併告警** | 這十個告警是不是同一件事？ | 從 trace 歸納出的呼叫關係，加上時間相近 | ⚠️ **規則為主**：有呼叫關係、同時發生就合併。AI 補沒有 trace 的部分 |
| **3. 定位到哪一段** | 慢或錯在哪個服務、哪一段？ | 比較「出事時的 trace」和「平常的 trace」，看哪一段的耗時、錯誤率變最多 | ⚠️ **統計就做得到**，AI 用來排序 |
| **4. 找出可能的原因** | 那一段為什麼變了？ | 同時間的變化：換版（`service.version`）、資源吃緊（metrics）、新出現的錯誤訊息（log） | ✅ **需要**：把幾百萬行 log 自動歸成樣式、找出突然變多的那種，要靠 AI |
| **5. 說明與建議** | 寫成人看得懂的結論 | 把證據整理成文字，對照處理手冊 | ✅ **適合用大型語言模型**，只負責整理與解釋，不負責判斷 |
| **6. 確認與回饋** | 結論對不對？ | 人確認，回饋給系統 | ❌ 人。回饋讓步驟 1、4 越來越準 |

### 例子

1. **發現異常（AI）**：mes-api 的回應時間在 10:05 偏離平常的樣子。
2. **合併告警（規則）**：mes-api、wip-worker、Oracle 同時告警；trace 顯示 mes-api → wip-worker → Oracle，合併成一件事。
3. **定位（統計）**：比對慢的 trace 和平常的 trace，wip-worker 查 Oracle 那段從 30 毫秒變 3 秒，其他段沒變。
4. **找原因**：規則找到 wip-worker 10:03 換版；AI 的 log 樣式分析發現 10:03 起新出現「full table scan on LOT_HISTORY」。
5. **說明（大型語言模型）**：「10:03 wip-worker 換版後，查 LOT_HISTORY 變成全表掃描，造成 mes-api 變慢；建議回退版本或檢查索引。」
6. **確認（人）**。

## 重點：怎麼知道「平常的樣子」

步驟 1 的品質決定整個流程。判斷錯了，後面全部白做：誤報太多，大家就不看了；漏報，出事了沒人知道。

### 1. 看哪些數字

不是每個 metrics 都要學，先從每個服務的核心指標開始：

| 對象 | 指標 | 從哪裡來 |
|---|---|---|
| 每個服務的每個 API（trace 的段名稱） | **流量**（每分鐘幾個請求）、**錯誤率**、**延遲**（p50、p95、p99，不要用平均） | trace；沒有 trace 的服務用應用自己的 metrics |
| 每個 Pod、節點 | CPU、記憶體、重啟次數 | kubelet、K8s 物件狀態 |
| 每個服務的 log | 每分鐘各 level 的筆數、**各種 log 樣式的筆數** | log |

**依什麼切開來學**：`service.name` × API（段名稱）× 指標。每個組合各學一份「平常」，一個服務慢不會被別的服務平均掉。這就是為什麼三種資料的服務欄位要統一。

### 2. 「平常」會隨時間變：週期

同一個服務，白天和半夜、平日和週末、換班前後，正常值本來就不一樣。學「平常」最重要的就是學這個週期：

```
延遲 p95
  │      ┌──┐      ┌──┐                        ┌──┐
  │   ┌──┘  └──┐┌──┘  └──┐      ...         ┌──┘  └─×  ← 這個點：比上週同一時段高很多 → 異常
  │───┘        └┘        └───               ──┘
  └──────────────────────────────────────────────────── 時間
     週一          週二                        下週一
```

同樣是 800 毫秒，在尖峰時段可能是正常，在半夜就是異常。所以比的是「**這個服務、在同一個週期位置（星期幾、幾點）的過去表現**」，不是一個固定數字。

廠內特有的週期也要考慮：換班、機台定期保養（PM）、月底結帳、大量投片。已知的事件做成行事曆，學的時候標出來，那段時間不要誤判。

### 3. 方法（由簡單到複雜）

| 方法 | 怎麼做 | 優點 | 缺點 |
|---|---|---|---|
| **A. 同時段的歷史範圍** | 取過去 4 週「同一個星期幾、同一個小時」的值，算中位數與離散程度（中位數絕對偏差），超出中位數 ± 3～5 倍就算異常 | 簡單、好解釋（「比過去四週同時段高 5 倍」）、不需要訓練 | 對漸漸變化、特殊日子不敏感 |
| **B. 拆出週期再看剩下的** | 把時間序列拆成「趨勢 + 每日週期 + 每週週期 + 剩下的」，只看「剩下的」有沒有異常 | 能處理趨勢（例如流量逐月成長） | 要調參數 |
| **C. 預測模型** | 用過去的資料預測現在「應該」是多少、範圍多大，實際值超出範圍就是異常 | 準度較好、能給信心區間 | 每個組合一個模型，數量多時要管理 |
| **D. 機器學習** | 讓模型自己找週期與分布（Elastic 的異常偵測就是這類，付費功能） | 自動、可同時看多個指標 | 比較像黑盒子，要有解釋 |

**建議從 A 開始**：

- 不用買授權、不用訓練，ES 的查詢加上一點 Python 就做得到。
- 結果好解釋，工程師比較願意相信。
- 先上線、收集回饋，知道哪裡不夠再換 B、C 或 D。

### 4. 讓「平常」學得準的條件

| 條件 | 為什麼 | 現在的狀態 |
|---|---|---|
| **歷史夠長** | 要看到週期，至少 4 週，最好 8 週；年度週期要 13 個月 | ⚠️ 方案見 [retention.md](retention.md)：metrics 降解析度留 400 天、log 與 trace 改留統計值 400 天 |
| **資料不缺、不重複** | 缺資料會被當成「流量掉到 0」，重複會被當成「流量暴增」，都是誤報 | ✅ 這個 repo 測過 ES 停機、當機、收集器重啟、換 key，都不掉、不重複 |
| **欄位一致** | 同一個服務在三種資料裡名稱要一樣，才切得出同一組 | ✅ `service.name`、`service.version`、`group` 三種資料一致 |
| **排除已知事件** | 學的資料裡如果混了事故、保養，「平常」會被拉偏 | ❌ 還沒有：需要事故紀錄、保養行事曆 |
| **換版後重新學** | 新版本的正常值可能不同；要分辨「新版變慢了（要告警）」和「新版本來就這樣（新的平常）」 | ⚠️ 欄位有了（`service.version`），規則還沒定 |
| **新服務** | 沒有歷史就沒有「平常」 | ❌ 還沒定：先用同類服務的範圍，或前兩週只記錄不告警 |

### 5. log 和 trace 的「平常」

- **log**：先把 log 歸成樣式（把變動的數字、ID 拿掉，例如「order * accepted」），再學「每種樣式平常每分鐘幾筆」。**新出現的樣式**和**突然變多的樣式**最有用。我們統一了 `message`、`log.level`、`error.type`，歸樣式比較準。
- **trace**：每個服務的每個 API（段名稱）學一份延遲分布。段名稱不能帶 ID（見 [apps/standards/tracing.md](../apps/standards/tracing.md)），不然每個請求都是不同的名稱，學不出來。

## 每一步要的資料，現在準備到哪裡

| 步驟 | 用到的資料 | 狀態 |
|---|---|---|
| 1. 發現異常 | metrics、trace 的流量／錯誤率／延遲；log 的樣式筆數 | ✅ 已收；⚠️ 歷史保留要拉長 |
| 2. 合併告警 | trace 歸納出的呼叫關係 | ✅ trace 已收；呼叫關係要從 trace 計算 |
| 3. 定位 | trace 每一段的耗時與狀態 | ✅ |
| 4. 找原因 | 換版（`service.version`）、資源 metrics、log 樣式 | ✅ |
| 5. 說明 | 前面的結果＋處理手冊 | ❌ 處理手冊還沒有 |

## 建議順序

1. **步驟 1**：用方法 A 對每個服務的核心指標做異常偵測。整個流程的起點，最快看到效果。
2. **步驟 3**：用 trace 定位到哪一段。純統計，效果明顯。
3. **步驟 4 的 log 樣式分析**：AI 最有價值的地方，能抓到人工翻 log 找不到的「新錯誤」。
4. **最後加大型語言模型做說明**：前面的證據越完整，它寫的結論越可靠。

步驟 1、4 的 AI 可以自己做（Python 從 ES 讀資料），也可以用 Elastic 的付費功能（異常偵測、log 樣式分群、log 量突變分析；免費授權實測都不能用，見 README 待辦）。

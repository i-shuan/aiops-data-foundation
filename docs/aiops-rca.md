# AIOps：根因分析怎麼做、哪裡需要 AI

一句話：**根因分析不是每一步都需要 AI。真正需要 AI 的是「找出不正常」和「從大量候選裡排出最可能的原因」；中間串資料的步驟，用查詢和規則就做得到。**

這份說明這個 repo 收進 ES 的 log、metrics、trace 要怎麼用來做根因分析，以及最關鍵的一件事：**怎麼知道「平常的樣子」**。

## 三種資料各回答什麼

| | 回答的問題 | 例子 |
|---|---|---|
| metrics | **有沒有出事、什麼時候開始** | 「mes-api 的回應時間從 10:05 開始變慢」 |
| trace | **一個請求經過哪些服務、哪一段造成的** | 「慢在 wip-worker 查 Oracle 那一段，從 30 毫秒變 3 秒」 |
| log | **那一段裡面發生了什麼事** | 「wip-worker 10:03 起出現 full table scan on LOT_HISTORY」 |

三種都用同一套欄位（`service.name`、`service.version`、namespace、Pod、`group`／`dept`），log 的 `trace.id` 對得到 trace 的 `trace_id`，所以串得起來。

### 分工：metrics 決定什麼時候告警，trace 和 log 說明原因

```
[過去 4 週的歷史資料]
        │
        ▼
【metrics 算 baseline】 ──────► 學出「平常週二 10:00」：
                                  • 請求量：1,200 ~ 1,500 次／秒
                                  • 延遲 p95：180 ~ 240 ms
                                  • 錯誤率：< 0.1%
                                        │
────────────────────────────────────────┼──────────────────────────
                                        ▼ 即時比對
【即時偵測：發現偏離】 ────────► 現在：延遲衝到 2,800 ms（異常）
                                        │
                                        ▼ 只調出異常那段時間
【trace 定位到哪一段】 ────────► mes-api → wip-worker → Oracle，
                                  慢在 wip-worker 查 Oracle（30 ms → 3 s）
                                        │
                                        ▼
【log 提供證據】 ──────────────► wip-worker 10:00 ~ 10:05 的 log：
                                  • 錯誤樣式：「Connection pool timeout」
                                  • 上下文：「DB host: 10.0.1.5:5432」
```

**為什麼 baseline 用 metrics 算：**

| | metrics | trace | log |
|---|---|---|---|
| 每個請求都有算到 | ✅ 應用自己記，每個請求都算 | ❌ 有取樣，調到一成就只看到一成 | ❌ 正常的請求通常不印 log |
| 延遲分布（p95、p99） | ✅ 直方圖 | ⚠️ 被取樣的那些 | ❌ 算不出來 |
| 歷史能留多久 | ✅ 可降解析度，留 1 年以上 | 7 天 | 原文 30 天 |
| 4 週算一次的成本 | 很低：已經是統計好的數字 | 高 | 中：只數筆數不讀原文還算快 |

所以 baseline 的流量、錯誤率、延遲**從 metrics 算**（應用的 `http.server.request.duration`，見 [aiops/baseline](../aiops/baseline/README.md)）。log 只學「每個服務每 5 分鐘有幾筆 error」這種筆數：它能抓到 metrics 看不到的問題（例如背景工作一直失敗，但 API 都正常）。trace 和 log 原文主要在**告警之後**用：只查異常那段時間，不需要長期保留。

## 根因分析的六步

| 步驟 | 要回答的問題 | 用什麼做 | 需不需要 AI |
|---|---|---|---|
| **1. 發現異常** | 哪裡不正常？ | 每個服務、每個時段學出「平常的樣子」，偏離就標出來（見下一節） | ✅ **需要**。固定門檻在幾百個服務上不可行：每個服務的正常值不同，白天晚上也不同 |
| **2. 合併告警** | 這十個告警是不是同一件事？ | 從 trace 歸納出的呼叫關係，加上時間相近 | ⚠️ **規則為主**：有呼叫關係、同時發生就合併。AI 補沒有 trace 的部分 |
| **3. 定位到哪一段** | 慢或錯在哪個服務、哪一段？ | 比較「出事時的 trace」和「平常的 trace」，看哪一段的耗時、錯誤率變最多 | ⚠️ **統計就做得到**，AI 用來排序 |
| **4. 找出可能的原因** | 那一段為什麼變了？ | 同時間的變化：換版（`service.version`）、資源吃緊（metrics）、新出現的錯誤訊息（log） | ✅ **需要**：把幾百萬行 log 自動歸成樣式、找出突然變多的那種，要靠 AI |
| **5. 說明與建議** | 寫成人看得懂的結論 | 把證據整理成文字，對照處理手冊 | ✅ **適合用大型語言模型**，只負責整理與解釋，不負責判斷 |
| **6. 確認與回饋** | 結論對不對？ | 人確認，回饋給系統 | ❌ 人。回饋讓步驟 1、4 越來越準 |

### 例子

1. **發現異常（AI）**：mes-api 的回應時間在 10:05 偏離平常的樣子。
2. **合併告警（規則）**：mes-api、wip-worker、Oracle 同時告警；trace 顯示 mes-api → wip-worker → Oracle，合併成一件事。
3. **定位（統計）**：比對慢的 trace 和平常的 trace，wip-worker 查 Oracle 那段從 30 毫秒變 3 秒，其他段沒變。
4. **找原因**：規則找到 wip-worker 10:03 換版；AI 的 log 樣式分析發現 10:03 起新出現「full table scan on LOT_HISTORY」。
5. **說明（大型語言模型）**：「10:03 wip-worker 換版後，查 LOT_HISTORY 變成全表掃描，造成 mes-api 變慢；建議回退版本或檢查索引。」
6. **確認（人）**。

## 重點：怎麼知道「平常的樣子」

步驟 1 的品質決定整個流程。判斷錯了，後面全部白做：誤報太多，大家就不看了；漏報，出事了沒人知道。

### 1. 看哪些數字

不是每個 metrics 都要學，先從每個服務的核心指標開始：

| 對象 | 指標 | 從哪裡來 |
|---|---|---|
| 每個服務的每個 API（trace 的段名稱） | **流量**（每分鐘幾個請求）、**錯誤率**、**延遲**（p50、p95、p99，不要用平均） | trace；沒有 trace 的服務用應用自己的 metrics |
| 每個 Pod、節點 | CPU、記憶體、重啟次數 | kubelet、K8s 物件狀態 |
| 每個服務的 log | 每分鐘各 level 的筆數、**各種 log 樣式的筆數** | log |

**依什麼切開來學**：`service.name` × API（段名稱）× 指標。每個組合各學一份「平常」，一個服務慢不會被別的服務平均掉。這就是為什麼三種資料的服務欄位要統一。

### 2. 「平常」會隨時間變：週期

同一個服務，白天和半夜、平日和週末、換班前後，正常值本來就不一樣。學「平常」最重要的就是學這個週期：

```
延遲 p95
  │      ┌──┐      ┌──┐                        ┌──┐
  │   ┌──┘  └──┐┌──┘  └──┐      ...         ┌──┘  └─×  ← 這個點：比上週同一時段高很多 → 異常
  │───┘        └┘        └───               ──┘
  └──────────────────────────────────────────────────── 時間
     週一          週二                        下週一
```

同樣是 800 毫秒，在尖峰時段可能是正常，在半夜就是異常。所以比的是「**這個服務、在同一個週期位置（星期幾、幾點）的過去表現**」，不是一個固定數字。

廠內特有的週期也要考慮：換班、機台定期保養（PM）、月底結帳、大量投片。已知的事件做成行事曆，學的時候標出來，那段時間不要誤判。

### 3. 方法（由簡單到複雜）

| 方法 | 怎麼做 | 優點 | 缺點 |
|---|---|---|---|
| **A. 同時段的歷史範圍** | 取過去 4 週「同一個星期幾、同一個小時」的值，算中位數與離散程度（中位數絕對偏差），超出中位數 ± 3～5 倍就算異常 | 簡單、好解釋（「比過去四週同時段高 5 倍」）、不需要訓練 | 對漸漸變化、特殊日子不敏感 |
| **B. 拆出週期再看剩下的** | 把時間序列拆成「趨勢 + 每日週期 + 每週週期 + 剩下的」，只看「剩下的」有沒有異常 | 能處理趨勢（例如流量逐月成長） | 要調參數 |
| **C. 預測模型** | 用過去的資料預測現在「應該」是多少、範圍多大，實際值超出範圍就是異常 | 準度較好、能給信心區間 | 每個組合一個模型，數量多時要管理 |
| **D. 機器學習** | 讓模型自己找週期與分布（Elastic 的異常偵測就是這類，付費功能） | 自動、可同時看多個指標 | 比較像黑盒子，要有解釋 |

**建議從 A 開始**（已實作：[aiops/baseline/](../aiops/baseline/README.md)）：

- 不用買授權、不用訓練，ES 的查詢加上一點 Python 就做得到。
- 結果好解釋，工程師比較願意相信。
- 先上線、收集回饋，知道哪裡不夠再換 B、C 或 D。

### 4. 讓「平常」學得準的條件

| 條件 | 為什麼 | 現在的狀態 |
|---|---|---|
| **歷史夠長** | 要看到週期，至少 4 週，最好 8 週；年度週期要 13 個月 | ⚠️ 方案見 [retention.md](retention.md)：metrics 降解析度留 400 天、log 與 trace 改留統計值 400 天 |
| **資料不缺、不重複** | 缺資料會被當成「流量掉到 0」，重複會被當成「流量暴增」，都是誤報 | ✅ 這個 repo 測過 ES 停機、當機、收集器重啟、換 key，都不掉、不重複 |
| **欄位一致** | 同一個服務在三種資料裡名稱要一樣，才切得出同一組 | ✅ `service.name`、`service.version`、`group` 三種資料一致 |
| **排除已知事件** | 學的資料裡如果混了事故、保養，「平常」會被拉偏 | ❌ 還沒有：需要事故紀錄、保養行事曆 |
| **換版後重新學** | 新版本的正常值可能不同；要分辨「新版變慢了（要告警）」和「新版本來就這樣（新的平常）」 | ⚠️ 欄位有了（`service.version`），規則還沒定 |
| **新服務** | 沒有歷史就沒有「平常」 | ❌ 還沒定：先用同類服務的範圍，或前兩週只記錄不告警 |

### 5. log 和 trace 的「平常」

- **log**：先把 log 歸成樣式（把變動的數字、ID 拿掉，例如「order * accepted」），再學「每種樣式平常每分鐘幾筆」。**新出現的樣式**和**突然變多的樣式**最有用。我們統一了 `message`、`log.level`、`error.type`，歸樣式比較準。
- **trace**：每個服務的每個 API（段名稱）學一份延遲分布。段名稱不能帶 ID（見 [apps/standards/tracing.md](../apps/standards/tracing.md)），不然每個請求都是不同的名稱，學不出來。

## 不同用途要的 baseline 不一樣

上面講的（[aiops/baseline/](../aiops/baseline/README.md) 已實作）是**「單一數字、依時段」的統計 baseline**：每條時間序列各自學「每個星期幾、每個小時，平常是多少、通常跳動多少」。它是**非監督式**的，不需要標好哪些是事故，只看歷史。

AIOps 的其他用途要的「平常」長得不一樣，有一部分可以共用這套：

| AIOps 用途 | 要回答的問題 | 要的「平常」長什麼樣 | 現在這套能不能用 |
|---|---|---|---|
| **指標異常** | 這個數字不正常嗎？ | 每條序列 × 每個時段的中位數、波動 | ✅ 就是這套 |
| **log 量異常** | 某個服務的錯誤 log 突然變多？ | 同上，數字是「每 5 分鐘的 log 筆數」 | ✅ 已經在學（`log.lines`、`log.errors`） |
| **log 樣式異常** | 出現以前沒見過的錯誤訊息？某種訊息突然變多？ | ① **樣式字典**：平常會出現哪些 log 樣式（例如「order * accepted」）<br>② 每種樣式平常每 5 分鐘幾筆 | ⚠️ ② 可以用這套；① 是另一種 baseline，要先把 log 歸成樣式、記下見過哪些 |
| **trace 延遲、錯誤** | 某個 API 變慢、錯誤變多？ | 每個服務 × API 的延遲分布、錯誤率 | ✅ 已經在學（`trace.*`） |
| **呼叫關係改變** | 出現以前沒有的呼叫？某條呼叫消失？ | **呼叫關係圖**：平常誰呼叫誰、每條線平常多少流量 | ⚠️ 每條線的流量可以用這套；「有哪些線」是另一種 baseline |
| **多個指標的關係** | CPU 變高但流量沒變？（可能是程式出問題，不是忙） | **指標之間的關係**：平常 CPU 跟流量的比例 | ❌ 這套一次看一個數字，看不出這種異常。要多變量的方法（迴歸、隔離森林之類） |
| **換版比較** | 新版本是不是變慢了？ | 依**版本**分開的分布（舊版 vs 新版） | ⚠️ 把 `service.version` 加進切分欄位就行，比較規則要另外寫 |
| **容量預測** | 再過多久硬碟、CPU 會不夠？ | **長期趨勢**（每月成長多少），不是週期 | ❌ 這套只學週期、不學趨勢。要預測模型 |
| **預測事故、自動判斷根因** | 這個模式以前是不是出過事？ | 過去的事故與當時的狀況 | ❌ 要**事故紀錄**當標註，是監督式學習 |

### 四種 baseline

1. **「數字 × 時段」**：現在這套。涵蓋指標、log 筆數、trace 延遲和錯誤，是最常用、也最先需要的一種。
2. **「集合」**：平常有哪些 log 樣式、有哪些呼叫關係。異常是「出現沒見過的」或「平常有的不見了」。
3. **「關係」**：多個指標之間平常的比例。
4. **「趨勢」與「標註」**：長期成長、過去的事故。

**共用的地基是同一套**：服務名稱、API、部門欄位一致；時間切成固定的時段；資料不缺、不重複。不管之後加哪一種，都不用回頭重整資料。

### 做的順序

| 順序 | 做什麼 | 狀態 |
|---|---|---|
| 1 | 「數字 × 時段」上線，累積資料與誤報、漏報的回饋 | ✅ 已完成（[aiops/baseline/](../aiops/baseline/README.md)） |
| 2 | **log 樣式字典**：抓「新出現的錯誤訊息」。歸好樣式後，每種樣式的筆數直接交給第 1 項學 | 下一步 |
| 3 | **trace 呼叫關係圖**：抓新出現或消失的呼叫，也用在根因分析的「合併告警」 | |
| 4 | **多指標關係、預測事故**：要先累積事故紀錄 | 有事故紀錄之後 |

## AIOps 訓練要多少資料

一句話：**訓練用的是「統計過的時間序列」，量很小（GB 等級）；真正的門檻是「時間夠長」、「資料品質」和「事故紀錄」。** 上 TB 的原始 log、trace 是給人查問題用的，不是給模型訓練用的。

### 量：以 200 個服務、500 個 Pod 估算

| 用途 | 訓練用的資料 | 筆數 | 大小 |
|---|---|---|---|
| **發現異常**（學「平常的樣子」） | 每個服務 × API × 指標（流量、錯誤率、p95、p99）＋每個 Pod 的資源，約 **1 萬條時間序列**；每條 8 週、5 分鐘一點（約 1.6 萬點） | 約 1.6 億點 | **約 2～3GB** |
| 同上，看年度週期 | 同樣 1 萬條，13 個月、1 小時一點（約 9,500 點） | 約 1 億點 | 約 1.5GB |
| **log 樣式** | 學樣式：每個服務抽 1～7 天的 log 原文（幾十萬行就夠）；學「平常幾筆」：每個樣式每 5 分鐘的筆數，8 週 | 樣式數萬種，大多數時段是 0 | 幾 GB |
| **定位到哪一段**（trace） | 不用訓練：每個 API 的延遲分布，2～4 週（應用的 `http.server.request.duration`） | — | 包含在上面 |
| **大型語言模型做說明** | 不用訓練：當下找到的證據＋處理手冊、過去事故的文字 | — | 文字，很小 |

一台 16～32GB 記憶體的機器就訓練得動，不需要 GPU；每天或每週重新學一次。

### 真正的門檻

| 門檻 | 要多少 | 為什麼 |
|---|---|---|
| **時間長度** | 至少 4 週，最好 8 週；年度週期要 13 個月 | 要看過完整的週期（星期幾、換班、月底、保養），不然會把正常的週期當成異常 |
| **資料品質** | 不缺、不重複、欄位一致 | 缺資料會被學成「平常就會掉到 0」，之後真的掉了也不會告警 |
| **事故紀錄** | 過去的事故：發生時間、影響範圍、根因；**幾十到幾百件** | 用來驗證「找出來的異常是不是真的事故」，以及之後訓練「預測會不會出事」、「自動判斷根因」這類模型。**這是最缺的，而且只能靠時間累積** |

**所以現在最該做的不是存更多資料，而是：**

1. 照 [retention.md](retention.md) 把長期統計值留下來（metrics 降解析度、log 與 trace 的統計），**從今天開始累積**。
2. **開始記錄事故**：每次出事記下開始和結束時間、影響哪些服務、根因是什麼。格式簡單就好，重點是持續記。幾個月後就是 AIOps 最有價值的訓練資料。

| 2. 合併告警 | trace 歸納出的呼叫關係 | ✅ | ⚠️ 呼叫關係圖已做（[aiops/rca](../aiops/rca/README.md) `topology`），合併還沒做 |
| 3. 定位 | trace 每一段的耗時與狀態 | ✅ | ✅ [aiops/rca](../aiops/rca/README.md)：慢在哪一段、錯誤從哪一段開始、瀑布圖 |
| 4. 找原因 | 換版（`service.version`）、資源 metrics、log 樣式 | ✅ | ⚠️ log：依 trace_id 撈各服務的 log、新出現的樣式（簡單規則）；換版、資源還沒接 |
| 5. 說明 | 前面的結果＋處理手冊 | ❌ 處理手冊還沒有 | ⚠️ 報告的「結論」一節用規則寫，還沒有大型語言模型 |

## 建議順序

1. **步驟 1**：用方法 A 對每個服務的核心指標做異常偵測。整個流程的起點，最快看到效果。
2. **步驟 3**：用 trace 定位到哪一段。純統計，效果明顯。✅ 已做：[aiops/rca](../aiops/rca/README.md) 從 baseline 的異常開始，照 Metrics → Trace → Log 查一遍，產出報告。
3. **步驟 4 的 log 樣式分析**：AI 最有價值的地方，能抓到人工翻 log 找不到的「新錯誤」。
4. **最後加大型語言模型做說明**：前面的證據越完整，它寫的結論越可靠。

步驟 1、4 的 AI 可以自己做（Python 從 ES 讀資料），也可以用 Elastic 的付費功能（異常偵測、log 樣式分群、log 量突變分析；免費授權實測都不能用，見 README 待辦）。

## 推進的兩個階段：先一般服務，再 EAP 與機台

先在一般服務（Web API、worker）把整套跑通：協定標準（HTTP、gRPC、DB、MQ）、呼叫鏈單純，問題好查。等這套流程驗證成熟，再接 EAP 與機台。底層的 ES、OTel Collector、baseline 程式都共用，EAP 主要是加解析規則和換欄位。

### 階段 1：一般服務（現在）

| 要做到的 | 狀態 |
|---|---|
| **三種資料對得起來**：每個請求有 trace，log 帶 `trace.id`、`span.id` | ✅ 已驗證（[traces.md](traces.md)） |
| 從 metrics（延遲、錯誤率）直接跳到那段時間的慢 trace | ✅ [aiops/rca](../aiops/rca/README.md)：從異常的服務、API、時間找出最慢的請求，再用 trace_id 撈各服務的 log |
| **baseline**：4 週同時段的中位數＋MAD | ✅ 程式完成，模擬資料驗證通過（[aiops/baseline](../aiops/baseline/README.md)） |
| baseline：MAD 為 0（值都一樣）時不亂報 | ✅ 有下限：中位數的 5%、或固定值，加上 `min_abs` |
| baseline：連續幾個點都異常才報，避免單點抖動 | ❌ 還沒做 |
| baseline：在真實的白天尖峰、半夜離峰確認範圍貼得住 | ⏳ 要先累積 4 週的真實資料 |
| **事故紀錄**：每次出事記下時間、影響範圍、根因，用來對帳哪些是真異常 | ❌ 格式和寫入方式還沒做 |
| **合併告警**：下游 DB 卡住 → worker 堵塞 → API 變慢，依 trace 的呼叫關係合成一件事 | ⚠️ 呼叫關係已經能從 trace 算（`aiops_rca topology`），合併還沒做 |

### 階段 2：EAP 與機台（之後）

階段 1 成熟後再做。要準備的：

1. **SECS 的 log 解析規則**（需要真實 log 樣本，見 README 開頭）。SECS 一則跨多行，Collector 收的時候要先合併。
2. **欄位對照**：

   | | 一般服務（階段 1） | EAP／機台（階段 2） |
   |---|---|---|
   | 串起整件事的 ID | `trace.id`、`work_order.id` | `lot.id`、載具 ID、交易 ID |
   | 對象 | `service.name`、Pod | `equipment.id`、腔體、EAP 實例 |
   | 請求與回應 | HTTP 請求 → 200／500 | SECS 主訊息（例如 S2F41）→ 回覆（S2F42）與 ACK |
   | 延遲 | API 回應時間 p95、p99 | 機台交握耗時、T3 逾時 |
   | 異常 | 5xx 突增、慢查詢 | 機台告警（S5F1）、命令被拒（HCACK ≠ 0） |

   `lot.id`、`equipment.id` 已定案；載具、腔體、交易 ID、EAP 實例的欄位名稱還沒定，要先跟平台確認。
3. **trace 只到 EAP 為止**：機台不會把 `trace_id` 傳回來，EAP 的 log 一定要寫 `trace_id`，才能從機台事件對回請求（見 [tracing.md](../apps/standards/tracing.md)）。
4. **baseline 加 EAP 的序列**：在 `series.yaml` 加機台交握耗時、逾時次數、告警次數等，依 `equipment.id` 切。程式不用改。

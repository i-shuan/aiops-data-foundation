# 清資料：餵給 baseline 前的資料檢查（2026-10）

**狀態**：盤點與規劃完成；檢查程式另開分支做　　**日期**：2026-10-23　　**相關**：[rca/README.md「髒資料排除」](../rca/README.md#髒資料排除)、`aiops/aiops_baseline/model.py`、`es.py`

**一句話**：資料進來時已經洗過（可信、不重複、格式統一）；但**拿去學「平常的樣子」之前，還沒有挑掉壞資料**，壞習慣、事故、壓測、假日都會被學成正常。

## Plan：要解決什麼

- **問題**：baseline 看過去 4 週學「平常」。如果那 4 週混了壞資料，就學錯：
  - 服務天天噴 1,000 個錯沒人修 → 學成「噴 1,000 個是正常」，真的出事反而不報。
  - 上禮拜出過事故 → 那段異常數字進了歷史，「平常」被拉歪。
  - 壓測、假日、維護 → 數字本來就不同，但系統不知道。
- **目標／驗收**：訓練前有一道檢查，挑掉或標記壞資料；每一項都能用故意放進去的壞資料驗證（例如插入一段事故再訓練，baseline 不被拉偏）。
- **做法**：先盤點程式現在已經擋了什麼，再補缺口。

## Do：盤點現況（對照程式）

**已經擋住的**（讀 `aiops/aiops_baseline/model.py`、`es.py` 確認）：

| 防護 | 做法 | 位置 |
|---|---|---|
| 少數幾次事故不會拉歪平常 | 用中位數加 MAD，不用平均 | `_stats` |
| 稀少筆數裡的爆量 | 卜瓦松：機率小於 0.001 的值先壓到上限再平均，重複到穩定 | `_poisson_stats` |
| 量太少的時間窗是雜訊 | 事件數不夠（比例類每窗少於 20 個請求）當「不知道」，不學也不判斷 | `mask_thin` |
| 歷史不夠不亂報 | 同星期幾×小時至少 2 天、每天同小時至少 3 天、不分時段至少 50 點，不夠就往下退層，再不夠就不給 baseline | `train`、`series.yaml` 的 `train` |
| 收集系統停機不是零流量 | 筆數類補 0 時，服務上線前、整個系統都沒資料的時段當「不知道」 | `es.py` `_fill_zero` |
| 剛結束的時間窗還沒收齊 | 往前退 30 秒（`lag`）再看 | `series.yaml` |
| 慢性病「偵測得到」 | N+1、吞掉的例外、新出現的 log 樣式有規則 | `rules.yaml`、`trace.yaml` |

**搜尋確認沒有的**：在 `aiops_baseline`、`aiops_common`、`aiops_rca` 和 `aiops/baseline/*.yaml` 搜尋 exclude、calendar、holiday、行事曆、quality、chronic、loadgen、maintenance、incident，**沒有任何命中**。

## Check：結果對不對

| 項目 | 現況 | 說明 |
|---|---|---|
| 訓練時排除事故時段 | ❌ | 沒有程式；要靠事故紀錄（也還沒有） |
| 行事曆（假日、維護、活動） | ❌ | 沒有 |
| 慢性病清單 | ❌ | 偵測得到，但沒有「每週列前 10 名並附負責人」 |
| 已知問題先靜音 | ⚠️ | `tune` 指令可固定粒度或調門檻，但沒有到期日、負責人欄位的強制 |
| 資料品質檢查（序列數暴增、必填欄位缺很多、資料突然停） | ❌ | 沒有 |
| 排除測試流量（壓測、loadgen） | ❌ | 沒有，也沒有約定用什麼 label 標 |

**現有防護的限制**：
- 中位數加 MAD 只擋得住「少數」。如果慢性病**天天**發生，它就是中位數本身，擋不住。
- 事故若連續很多天（例如兩週的長期降級），一樣會把中位數拉走。
- `mask_thin` 只看量，不看資料對不對（路由沒參數化時，量夠但序列數爆炸，它不會管）。

## Act：決定與後續

- **決定**：這份紀錄只做盤點與規劃，先合進 master 讓團隊對方向有共識；檢查程式另開分支，依下面順序拆成獨立任務。
- **順序**（實作成本低、保護效益高的先做）：
  1. **資料品質檢查**（純規則，不靠外部狀態，最好寫單元測試，也能擋住髒維度把算力撐爆）：
     - 每條序列的 `by` 值（服務、路由）數量比昨天暴增 → 多半是路由沒參數化（例如 `/orders/123` 沒換成 `/orders/{id}`）。
     - 必填欄位（`service.name`、`k8s.pod.name`、`trace.id`）缺失比例。
     - 某個服務的資料突然停了。
     - `unassigned` group 的資料量突然變多（`dept` 清單漏同步的徵兆）。
  2. **排除已知干擾**：訓練前依設定檔排除指定時間區間（事故、維護，例如 `exclude_windows`），和帶測試標記（壓測、loadgen）的資料。只要一個設定加查詢條件，直接解決「長期事故把 baseline 拉歪」。
  3. **慢性病清單、行事曆**：需要人工維護清單或接外部日曆，規則會隨業務變，等前兩道穩了再加。
- **要改的**：`aiops/aiops_baseline` 新增檢查指令，結果寫 `aiops-*` index；`docs/pdca/README.md` 的 Check 表更新狀態。
- **未驗證**：沒有用真實資料量過這些檢查要多久、誤報多少；門檻要等排程跑 2～4 週再校。
- **下一輪要驗證**：故意送一批沒參數化的路由，確認會被檢查抓到；插入一段事故再訓練，baseline 是否被拉偏。

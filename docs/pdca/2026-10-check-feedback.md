# Check：事故紀錄與值班回饋（2026-10）

**狀態**：已完成（已合進 master）；告警出口、版本、回測沒做　　**日期**：2026-10-24　　**相關**：[feedback/README.md](../feedback/README.md)、[排除已知干擾](2026-10-exclude-adjust.md)
**模組**：⑨ feedback（含 ⑧ 出口的事故紀錄）

## Plan：這一次要達到什麼

- **需求**：告警送出去之後，沒有地方記「這筆是真的還是誤報」，也沒有地方記事故。於是量不出誤報率，不知道哪個門檻不準；確認過的事故也沒法告訴 baseline「這段別學」。PDCA 的 Check 是空的。
- **目的**：
  1. 值班可以對每筆告警標記：真的、誤報、根因錯、漏報。
  2. 算得出每條序列的誤報率、已標記比例。
  3. 同一個對象誤報累積多次時，能提出放寬門檻的建議；**不自動生效**，單次回饋不動門檻。
  4. 事故可以記錄，並能一鍵提出「這段不學」的建議。
- **範圍**：先收集與統計。不做告警出口（通知）、不做版本／回測／評測集、不做網頁或通知裡的按鈕。

幾個設計決定：
- 只算 `status: anomaly` 的當告警；`warning` 還沒通知任何人。規則、跟兄弟比、品質檢查沒有 `status`，是直接通知的，算告警。
- 同一筆異常被標記多次，以最後一筆為準；同一個人再標會覆蓋。為什麼：誤報要「累積多次」才提建議，不能被同一個人重複點擊湊滿。
- 建議的 `match` 是完全符合那個對象（欄位值前後加 `^$` 並跳脫），`status: proposed`。為什麼：只調那一個對象，而且要人核准。

## Check：測試的目的與結果

| 測試目的（為了確認什麼） | 怎麼測 | 結果 |
|---|---|---|
| 統計口徑對不對：warning 不算告警；規則（沒有 `status`）算告警 | 單元測試＋ES 灌 14 筆異常（含 1 個 warning、1 個規則） | `pending` 列 13 筆，warning 沒列，規則有列 |
| 防污染：重複標記不能湊出「累積多次」 | 兩個人對同一筆標誤報；同一個人先標誤報再改真的；同一筆標 5 次誤報 | 兩個人標同一筆只算一次；改主意的覆蓋；同一筆標 5 次不構成候選 |
| 誤報率與候選的算法 | 同一個對象標 4 次誤報、1 次真的；另一個對象標 2 次 | 該序列誤報率 80%；只有標 4 次的列為候選，標 2 次的不列 |
| 漏報（沒有異常 id）能不能記、不重複列 | 用 `--series --match --at` 標漏報 | 列在漏報，同一對象不重複 |
| 建議只提該提的、不重複、不生效 | `suggest` 跑兩次；看 `override_for`；`approve` 前後比較 | 只對誤報 ≥ 3 次的對象提一筆（z 5 → 7）；第二次不重複；`proposed` 時沒有任何作用 |
| 核准後影響範圍有沒有超出那個對象 | 同服務另一條路由（`/health`）、名稱相近的服務（`mesXapi`）、序列名稱只差一個字元 | 都不受影響；路由裡的 `{id}`、服務名裡的 `-`、`.` 都有跳脫 |
| 事故能不能同時提「這段不學」，且要核准才生效 | 事故加 `--exclude-training`；`approve` 前後各跑一次 `train` | `approve` 前不排除；後排除那段（7,200 個點）；沒列服務的事故，建議是對全部 |
| 輸入錯誤有沒有清楚訊息、不寫入 | 不存在的 id、錯的 verdict、缺參數 | 都有訊息，沒有寫入 |

這輪測試**沒有發現需要修的程式問題**。

沒測到：多人同時標記；很多筆（上千）時的速度。

## Act：Check 後沒改善的、還沒解決的

| 沒改善的 | 在什麼情況下發現的 | 影響 | 後續 |
|---|---|---|---|
| [⑧] 沒有告警出口 | 範圍外；實測時 `pending` 只能自己查 | 值班收不到通知，也不知道有哪些待標記 | 告警出口（收斂之後） |
| 沒有版本、回測、評測集 | 文件規定「回測通過才調門檻」，但沒有回測工具 | `suggest` 的建議沒辦法先回測就核准，目前只靠人把關 | 版本、回測、評測集（待排） |
| 回饋靠指令標記 | 實測全是用指令 | 值班不一定願意開終端機，標記率可能很低 | 做在通知裡的按鈕或簡單網頁 |
| 誤報率可能偏高或偏低（推論） | 統計只算「被標記」的；`reviewed_rate` 看得到比例 | 若只有覺得煩的才標，誤報率偏高 | 看已標記比例，比例低時不下結論 |
| `suggest` 只調 z，不調 `min_abs`、粒度 | 讀 `suggest_override` | 誤報原因若是 `min_abs` 太小，調 z 效果有限 | 視回饋再擴充 |
| 「3 次」「× 1.4」是估的 | 沒有真實回饋可校 | 太敏感或太遲鈍 | 正式環境跑幾週再校 |
| 事故一次影響多個服務會產生多筆建議，要分別核准（推論） | 讀程式；實測只測了單一服務與不列服務兩種 | 核准麻煩 | 評估一次核准同一事故的全部建議 |
| [⑨] 事故的根因沒有餵給 RAG／LLM | 範圍外 | 確認過的根因沒有被重複利用 | LLM 摘要那一輪 |

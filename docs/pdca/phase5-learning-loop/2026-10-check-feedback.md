**狀態**：已完成（已合進 master）；告警出口、版本、回測沒做　　**日期**：2026-10-24　　**相關**：[feedback/README.md](../../feedback/README.md)、[排除已知干擾](../phase2-anomaly/2026-10-exclude-adjust.md)
**模組**：⑨ feedback（含 ⑧ 出口的事故紀錄）

## Plan：這一次要達到什麼

- **需求**：告警送出去之後，沒有地方記「真的還是誤報」，也沒有地方記事故。
  - 量不出誤報率，不知道哪個門檻不準。
  - 確認過的事故沒法告訴 baseline「這段別學」。
- **目的**：
  1. 值班可以對每筆告警標記：真的、誤報、根因錯、漏報。
  2. 算得出每條序列的誤報率、已標記比例。
  3. 同一個對象誤報累積多次時，提出放寬門檻的建議；**不自動生效**，單次回饋不動門檻。
  4. 事故可以記錄，並能一鍵提出「這段不學」的建議。
- **範圍**：先收集與統計。不做告警出口（通知）、版本／回測／評測集、網頁或通知裡的按鈕。

## Check：測試的目的與結果

| 測試目的（為了確認什麼） | 怎麼測 | 結果 |
|---|---|---|
| 統計口徑：warning 不算、規則算 | 單元測試＋ES 灌 14 筆異常（含 1 warning、1 規則） | `pending` 列 13 筆：warning 沒列，規則有列 |
| 防污染：重複標記湊不出「累積多次」 | 兩人標同一筆誤報；一人改主意；同一筆標 5 次 | 兩人同一筆只算一次；改主意的覆蓋；標 5 次不構成候選 |
| 誤報率與候選的算法 | 對象 A 標 4 次誤報、1 次真的；對象 B 標 2 次 | A 序列誤報率 80%；只有 A 列為候選 |
| 漏報（沒有異常 id）能記、不重複列 | `--series --match --at` 標漏報 | 列在漏報，同一對象不重複 |
| 建議只提該提的、不重複 | `suggest` 跑兩次 | 只對誤報 ≥ 3 次的對象提一筆（z 5 → 7）；第二次不重複 |
| 建議 `proposed` 時不生效 | 看 `override_for`；`approve` 前後比較 | `proposed` 時沒有任何作用 |
| 核准後只影響那個對象 | 同服務 `/health`、相近的 `mesXapi`、只差一字元的序列 | 都不受影響；`{id}`、`-`、`.` 都有跳脫 |
| 事故提「這段不學」，核准才生效 | 事故加 `--exclude-training`；`approve` 前後各跑 `train` | 前不排除；後排除那段（7,200 點） |
| 沒列服務的事故 | 同上 | 建議對全部服務 |
| 輸入錯誤 | 不存在的 id、錯的 verdict、缺參數 | 都有訊息，沒有寫入 |

沒有發現需要修的程式問題。

# 產品主線：從收值到 learning loop 的 8 步（2026-10）

**狀態**：進行中（計畫＋現況盤點，還沒動工）　　**日期**：2026-10-25　　**相關**：分支 `claude/product-loop`（從 `claude/alert-exit` 開）
**模組**：①～⑨ 全部（下面每一步標它屬於哪個模組；**編號仍以 ①～⑨ 為準**，8 步是產品的說法）

## Plan：這一次要達到什麼

- **需求**：要把 **learning loop**、**老師傅 feedback**、**RCA 結合 RAG** 當作產品賣點。現在零件大多做了，但沒有串成一圈：報告送不到人手上，老師傅的經驗存了也沒被拿出來用，所以只能展示「會偵測、會寫根因報告」，還不能展示「會學」。
- **目的**：照下面 8 步把整條線接起來，最後能跑通這一個故事（每一步都要能在這個故事裡指出來）：

  ```
  第 1 次：mes-api 變慢 → 告警＋根因報告送到值班
          → 老師傅回饋：「真的，根因是 Oracle 統計資訊過期，處置是重跑 analyze，看 Oracle 段變慢就知道」
  第 2 次：類似症狀 → 報告最前面多一段：「跟 9/12 的事故相似；當時根因、處置、誰處理的」
  另一邊：月底批次被誤報 3 次 → 老師傅都標誤報 → 系統提建議 → 核准 → 下個月底不再報
  ```

- **範圍**：這一份是**主線計畫和盤點**，不改 code；每一步真正動工時各開一份 PDCA（已開的：[告警出口](2026-10-alert-exit.md)）。

### 8 步（產品的說法）對到模組

| 步 | 內容 | 模組 |
|---|---|---|
| 1 | 收值，三種資料共用同一套鑰匙（共同鑰匙圈） | ①（鑰匙名字統一屬 ②） |
| 2 | 清洗資料 | ② |
| 3 | 異常分析：**基本樣式**（學「平常的樣子」：baseline、trace 每一段）與**單次異常**（不用學、一次就算：規則、跟兄弟比） | ④（結果寫 ⑤） |
| 4 | 串 metrics → trace → log，抓出問題在哪 | ⑦ |
| 5 | 輔助第 4 步查問題的工具：呼叫關係、瀑布圖、log 樣式、用業務 ID 查一筆交易、給人和 LLM 用的查詢工具（**這是我對「輔助 4」的理解，不對再改**） | ⑦ |
| 6 | 整合事件：很多筆異常合成一件 | ⑥（送出去屬 ⑧） |
| 7 | 抓出根因，結合 RAG（附上過去相似事故、老師傅當時怎麼判斷、怎麼處置） | ⑦＋⑨ |
| 8 | learning loop：feedback 進來 → RAG 更新、異常分析的門檻與 baseline 調整 | ⑨（回饋入口屬 ⑧） |

8 步裡沒有寫到、但這條線一定要的：**⑧ 出口**（告警送到人、回饋從人回來）。沒有它第 6 步之後的東西都沒人看到，第 8 步也沒有回饋可以學。

| 步 | 有的（證據） | 狀態 | 缺的 |
|---|---|---|---|

| 2 清洗資料 | 進來時：格式統一、去重複、時區（[time-alignment](2026-10-time-alignment.md)）；Java 指標改名；被拒的進 failure store。餵 baseline 前：資料品質 `quality`（停了、缺欄位、路由爆炸、延遲、時鐘偏差、被拒收）、排除時段／重置點（`adjust`）、慢性病（`chronic`）、行事曆 | ✅ 程式｜⚠️ 沒排程 | 業務 ID（交易 ID）沒命名、沒從 log 抽；REST API log 的解析規則（要樣本） |
| 3 異常分析 | **基本樣式**：Median＋MAD（星期×小時，退階到每天同小時、不分時段）、trace 每一段的 baseline（`trace-train`、`trace-detect`）、連續才算（`status`、`streak`）。**單次異常**：39 條規則（容器重啟、副本不夠、資源快滿…＋錯誤率 5%、p95 2 秒保底）、跟兄弟比（`peer`）。結果都寫 `aiops-anomalies` | ✅ 程式（k3s 驗過）｜⚠️ 沒用真實資料跑過、沒排程 | 門檻都是估的；正式環境只寫入不通知跑 2～4 週 |
| 4 串 metrics → trace → log | `aiops_rca investigate`：從異常拿服務＋路由＋時間 → 撈出事時最慢 200、出錯 100 個 trace 跟一週前比 → 慢在哪一段（扣掉下游）、錯從哪開始 → 用 trace_id 撈 log、新出現的 log 樣式。產出 Markdown 報告（`aiops/rca/example-report.md`） | ✅（k3s 驗過） | 每一段用平均，少數極慢的會拉偏（[metrics-to-trace](2026-10-metrics-to-trace.md) 的 Act）；瀑布圖、撈 log 只用最慢的 1 筆 |
| 5 輔助查問題 | 呼叫關係圖（`topology`、mermaid）、瀑布圖、log 樣式比較 | ⚠️ | 用業務 ID 查一筆交易的時間線（等業務 ID）；給 LLM 用的查詢工具（查某服務的 trace、某段 log 樣式、某 API 的 p95）；Kafka 那段斷鏈要靠業務 ID 補接 |
| 6 整合事件 | 只有「同一條序列連續才算」 | ❌ | 同服務合成一件、沿呼叫關係合併上下游、排優先（[system-stages 第 7 節](../system-stages.md)）；告警出口（[alert-exit](2026-10-alert-exit.md)，只有 Plan） |
| 7 RCA＋RAG | 根因報告（第 4 步）；事故紀錄 `aiops-incidents` 存症狀、根因、處置、相關異常 | ⚠️ RCA ✅｜RAG ❌ | **報告不會去找過去的事故**：`aiops_rca` 完全沒讀 `aiops-incidents`、`aiops-feedback`。沒有相似事故檢索、沒有 LLM 摘要；沒有評測集（20～30 件過去事故） |
| 8 learning loop | `feedback add`（真的／誤報／根因錯／漏報＋正確根因）；`feedback suggest`：同一個對象誤報 3 次 → 提「放寬門檻」（proposed）；`adjust approve` 才生效；`incident add --exclude-training` 提「這段不學」；`tune` 調粒度、z | ⚠️ | **回饋只能打指令**，老師傅不會用；沒記「怎麼看出來的」（老師傅經驗的核心）；回饋不會更新 RAG（因為沒有 RAG）；漏報不會變成新規則；沒有「學之前、學之後」誤報率、找到原因時間的數字；沒有回測 |

**總結**：1～4 是穩的，5 有一半，**6、7 的 RAG、8 的入口是斷點**。賣點的三個字：RCA 有了；老師傅 feedback 有存的地方、沒有給老師傅用的入口；learning loop 有「誤報 → 建議放寬」這一小圈，沒有「經驗 → RAG → 下一次報告」這一圈。

## Act：要補的（依順序：每一步都是那個故事缺的一環）

| 順序 | 做什麼 | 步／模組 | 為什麼排這裡 | 要先定的 |
|---|---|---|---|---|
| 1 | **告警出口＋最小收斂**：同服務合成一件、一件一則通知＋報告；先 dry-run 記基準 | 6／⑥⑧ | 沒有它老師傅看不到報告，後面全部沒有輸入 | 通知管道；每個 group 送給誰；夜間要不要發 |
| 2 | **老師傅的回饋入口**：通知上就能標（真的／誤報／根因錯），多三格：根因、處置、**怎麼看出來的**；寫進現有的 `aiops-feedback`、`aiops-incidents` | 8／⑧⑨ | 指令列沒人用；「怎麼看出來的」就是要留下來的經驗 | 跟通知同一個地方（Teams 卡片按鈕、表單網頁…） |
| 3 | **相似事故檢索（RAG 的 R）**：新的一件用服務、異常的指標組合、慢的那段、錯的源頭、log 樣式，去 `aiops-incidents` 找最像的幾件，附在報告最前面；**先不用 LLM**，用 ES 檢索，結果看得出為什麼像 | 7／⑦⑨ | RAG 的價值在「找得到」；先做可解釋的檢索，比先上 LLM 可靠 | 用什麼資料：k3s 造的事故，還是試點產線的歷史事故 |
| 4 | **回饋更新 RAG**：老師傅確認的事故直接進檢索庫；「根因錯」記正確根因；同樣根因 ≥ 3 次 → 提「升級成規則」 | 8／⑨ | 讓第 2 次比第 1 次好 | — |
| 5 | **門檻、baseline 調整接回饋**：現有 `feedback suggest`（誤報 3 次 → 放寬）加回測（用新設定重跑過去 4 週，事故還抓得到才給核准）；漏報 → 提新規則或降門檻 | 8／④⑨ | 現在的建議沒有回測，核准的人不知道改了會不會漏 | — |
| 6 | **LLM 摘要（RAG 的 G）**：讀報告＋相似事故，寫成「原因、影響、建議處置」一段話，只加註不擋告警；改 prompt 前跑評測集 | 7／⑦⑨ | 前面證據齊了它寫的才可靠，所以放後面 | 用哪個模型、能不能連外 |
| 7 | **量化**：學之前、學之後的誤報率、從告警到找到原因多久、老師傅回饋了幾件 | 8／⑨ | 賣「會學」一定要數字 | 試點產線 |
| — | 第 5 步的工具（業務 ID 查交易、給 LLM 的查詢工具） | 5／⑦ | 等業務 ID 命名、log 樣本；LLM 工具跟順序 6 一起 | 業務 ID 名稱 |

- **還沒解決、要誠實面對的**：
  - **沒有真實事故資料**（在什麼情況下發現：盤點第 3、7 步時，所有驗證都是 k3s 造的）。展示可以用造的，賣的時候客戶會問「實際降了多少誤報」，需要一個試點產線跑 1～2 個月。
  - **RAG 要有料**：至少 20～30 件過去的事故（症狀、根因、處置）。工廠有舊的事故單、交接紀錄的話，現在就該開始收。
  - **第 5 步的意思是我推的**（「輔助 4 查問題」），不對要改。
- **決定**：不再加新的偵測機制；照上表順序把這一圈接起來。之前評估「adjust、feedback 偏早」是從可靠度看的；它們是賣點的零件，留著，但不再擴。

# metrics 異常怎麼找到對的 trace（2026-10）

**狀態**：Plan、Do、Check 完成；Act ② 還沒改程式　　**日期**：2026-10-23　　**相關**：[rca/README.md](../rca/README.md#metrics-異常怎麼串到-tracelog)、`aiops/aiops_rca/`

## Plan：要解決什麼

問題：metrics 只有統計數字、不帶 trace_id，根因分析只能用「服務＋路由＋時間」去找 trace，不保證是同一個請求。想法：用 exemplar（metrics 夾帶一個請求的 trace_id）直接綁定

## Do：實際做了什麼

實測 ES 9.5.5＋Collector contrib 0.162.0：帶 exemplar 的 metrics 走 `/_otlp/v1/metrics`（正式路線）和 Collector 的 `elasticsearch` 寫入元件，存進去都沒有 exemplar（`_source`、mapping、全文搜尋都找不到 trace_id）

測試用的腳本是自己組 OTLP metrics（每種型別各夾一個 exemplar）直接 POST 到 ES；沒有放進 repo。

## Check：結果對不對

① 這個架構做不到 exemplar；② 就算做得到，exemplar 只是一個隨機樣本，不是「造成異常的那個請求」（p95 變高是幾千個請求的結果），而且正常的 trace 只留 5%，常常點過去是空的；③ 對照程式：根因分析**已經**撈一批（最慢 200 個＋最多 100 個出錯的）跟一週前同時段比每一段的時間，不是只看一筆；只有瀑布圖、用 trace_id 撈 log 只用最慢的 1 筆

## Act：決定與後續

① 不做 exemplar，不動 Collector、ES、應用端；② 改根因分析（`aiops/aiops_rca`）：每段除了平均，加「這批慢請求裡有幾成的最大段是它」（例如 18／20 都卡在同一句 SQL）和中位數，避免一兩筆特例拉高平均；瀑布圖、撈 log 從 1 筆改成幾筆有代表性的（卡在主要瓶頸段的）

### 方案比較

| | exemplar（metrics 直接帶 trace_id，不採用） | 一批慢 trace 找共同瓶頸（採用） |
|---|---|---|
| 怎麼運作 | metrics 統計時，SDK 挑一個請求的 trace_id 夾在數字旁邊 | metrics 異常時，用服務＋路由＋時間撈一批慢的、錯的 trace，統計大家共同卡在哪一段 |
| 做起來要多少工 | **現在做不到**：ES 9.5.5 不存 exemplar（實測）；硬做要自己寫一支程式把 exemplar 轉成文件，Java 那條（Prometheus 格式來抓、換算差值）還要另外驗證 | **低**：Collector、ES、應用端都不動，只改 `aiops/aiops_rca`（`analyze.py` 的統計、`__main__.py` 挑 trace） |
| 點過去查不查得到 | **常常查不到**：exemplar 指到正常請求時，那個 trace 有 95% 被尾端取樣丟掉 | 慢（> 1 秒）、錯的、有例外的**全留**，撈得到；但比 1 秒快的變慢（例如 200ms → 800ms）只剩隨機 5% 可用 |
| 根因準不準 | **低**：只有一個樣本，剛好遇到 GC 停頓、網路抖動就會帶偏 | **較高**：看「20 筆裡 18 筆卡同一句 SQL」這種多數現象，特例不會主導；但仍是「同時間、同路由」的關聯，同時有兩種問題要再分群 |
| 維運 | 多一個元件要顧，多一個可能掉資料的地方 | 用現有的 index 和程式，不多元件 |

### 小結

- **不用 exemplar 失去的**：在圖上點某一個點，直接跳到產生那個點的那一個請求。這主要是人看圖時用的；對自動化根因分析幫助不大，因為 p95 變高是幾千個請求的結果，本來就沒有「那一個請求」。
- **採用一批慢 trace 得到的**：避開 ES 的限制、不加元件，從「看一個樣本」變成「看多數請求的共同點」。
- **前提**：慢的、錯的 trace 全留（尾端取樣，已做）。保留 30 天、單獨放 `traces-problem` 在 `claude/retention` 分支，**還沒合進 master**；現在留下的 trace 都在同一個 index、不會刪。

### 採用做法的限制

| | 說明 |
|---|---|
| 出事時挑最慢的、平常隨機挑 | 兩邊樣本本來就不同，差距會被放大；排名可信，絕對值要保守看 |
| 每段目前用平均 | 一兩筆特別慢的還是會拉高平均；要加「幾成的請求最大段是它」和中位數（Act ②） |
| 依賴取樣門檻 | 1 秒以下的變慢，可用的 trace 少，結論弱 |

# ES 剛起來回 401，Collector 直接丟資料（2026-10）

**狀態**：已完成（repo 內的部分）　　**日期**：2026-10-24　　**相關**：分支 `claude/es-startup-401`；源自 [trace-durability](2026-10-trace-durability.md) 的 S4
**模組**：① 收值（三條線送 ES 的最後一段）

## Plan：這一次要達到什麼

- **需求**：ES 剛起來的幾秒對 API key 回 **401**，Collector 判成永久錯誤（`Permanent error … 401`），把那幾批從佇列移掉。
  - 磁碟佇列、Kafka 都擋不住：它們擋「送不到」，不擋「送到了被拒絕」。
  - log、metrics 線用同一種 exporter（`otlp_http`），推論也會。
- **目的**：
  1. 量出 401 窗口：ES 啟動的哪一段、持續幾秒、哪種認證會遇到、ES 多台時會不會。
  2. 找到讓 Collector 不丟的做法並實測：ES 沒準備好時不回 401（回 503 或連不上，Collector 都會重試）。
  3. 回答「量大是不是一定要 Kafka」。
- **範圍**：只做「ES 沒準備好」這個情境。
  - API key 真的錯、被刪掉的 401 不在內：那時丟掉是對的，要靠告警。
  - 不改 ES 的部署方式（中央 ES 不在這個 repo）。

## Check：測試的目的與結果

**環境**：docker，ES 9.5.5、Collector contrib 0.162.0、HAProxy 3.1。測 trace 線的 trace-sampler → ES 那段（log、metrics 用同一種 exporter）。

### 401 窗口

| 測試目的（為了確認什麼） | 怎麼測 | 結果 |
|---|---|---|
| 401 持續多久 | 重啟 ES，每 0.1～0.3 秒用 API key 打 GET /；對照 ES log | 從 log `started` 起 **0.9～1.3 秒**（5 次：0.88、0.92、1.3、1.9、2.7 秒） |
| 窗口裡別的認證 | 同上，同時用 elastic 帳號打 | elastic 帳號 GET / 200、`/_cluster/health` 200（status red） |
| 窗口什麼時候結束 | 對照 ES log | `.security` index 的 shard 起來（RED→YELLOW）時 |
| 窗口裡 ES 的 log | 同上 | `Authentication using apikey failed` |
| `/_cluster/health` 能不能當健康檢查 | 記 health 第一次 200 的時間 | **不能**：跟 401 開始同一秒（3 次都是） |
| `/_cluster/health/.security*?wait_for_status=yellow` 能不能 | 同上 | 不準：3 次裡 1 次 yellow 之後 API key 還 401 了 0.5 秒 |

- **只有用 API key 自己打，才對得到「API key 能用」的時間點。**

### Collector 會不會丟

| 測試目的（為了確認什麼） | 怎麼測 | 結果 |
|---|---|---|
| 直連 ES、ES 重啟（S5） | trace-sampler 一直在跑（磁碟佇列、退避 1～30 秒），t=30 重啟 ES，3,000 個 trace | 掉 0、沒有 401：退避沒撞到窗口 |
| 重試一定落在窗口裡 | 同 S5，重試固定 1 秒（`sampler-fastretry.yaml`，只為測試） | **掉 420 個 trace**：10 筆 `Permanent error … 401`，`dropped_items` 共 400 段 |
| 經過「用 API key 檢查」的 LB | 同上；Collector 改送 HAProxy（API key 打 GET /，0.5 秒一次） | **掉 0**：Collector 收 210 筆 503，全部重試成功 |
| readinessProbe 的指令 | 對 docker 的 ES 跑：有 key 檔、空的 key 檔、錯的 key | 有 key → 0（Ready）；空的 → 退回 health → 0；錯的 → 非 0（Not Ready） |

- 直連時撞不撞到窗口看運氣（trace-durability 的 S4 也是：現況撞到、A2 兩次沒撞到）。
- HAProxy log：ES 停 → DOWN（connection refused）→ ES 起來 → 連續 2 次 200 → UP。

### 兩台 ES

| 測試目的（為了確認什麼） | 怎麼測 | 結果 |
|---|---|---|
| 只重啟一台，有沒有窗口 | 同一容器兩個 ES；kill -9 一台再起，每 0.2 秒用 API key 打它 | 沒有（2 次）：連不上 → 直接 200（17.6、18.1 秒）；另一台全程 200 |
| 兩台一起重啟 | kill -9 兩台再起 | **有**：先起來的那台 401 持續 1.1 秒；第二台起來時直接 200 |

兩台 ES 走 LB 的端對端：HAProxy 輪流分配、trace-sampler 重試固定 1 秒。舊檢查＝elastic 帳號打 `/_cluster/health`（原本 readinessProbe 的做法），新檢查＝API key 打 GET /。

| 情境 | 舊檢查 | 新檢查 |
|---|---|---|
| 滾動重啟（一次一台，cluster green 再換下一台） | **掉 200～280**（3 次）；401 全部來自**活著的那台** | **掉 0**，沒有任何 401 |
| 兩台一起 kill -9 再起 | **掉 540**（27 批 401） | **掉 0**；LB 回 248 次 503，Collector 全部重試成功 |

- 兩台的叢集，投票名單只有一台（`_cluster/state` 的 `last_committed_config`；ES 會把投票數維持在奇數）。
- 重啟到有投票權的那台時沒有 master，活著那台也讀不到 `.security`，API key 一律 401。
- 這時 `/_cluster/health` 是 timeout（LB 舊檢查記 `Layer7 timeout`）；那台回來的瞬間 health 先好、API key 還沒好，舊檢查就把流量導過去。
- 上面「只重啟一台沒有窗口」，重啟的是沒投票權的那台。
- **結論**：兩台 ES 不算高可用，滾動重啟也有窗口；三台才能一台一台重啟不中斷（見 [troubleshooting](../../../troubleshooting.md)：兩個節點只有一台能投票）。

### 其他發現

- **ES 的 `_otlp` 入口整批被拒時仍回 200**：每筆的 FORBIDDEN 放在回應內容裡，Collector 的 `sent_spans` 照加、log 沒有錯誤。
  - 實測：測試用的 Collector 設定少了正式 `common.yaml` 的 `data_stream.namespace = group`，資料落到 `traces-generic.otel-default`，寫入 key 沒權限。
  - `otelcol_exporter_sent_spans` 5,240，ES 沒有 index，3,000 個 trace 一個都沒存。
- HAProxy 預設只在啟動時解析一次主機名：ES 換 IP 後一直 DOWN，Collector 一直收 503，資料留在佇列送不出去（沒丟）。加 `resolvers` 解決。
- K8s 的 Service IP 不會變，沒這個問題；LB 直接指 Pod／VM 主機名的要注意。
- HAProxy 兩個 server 用同一個主機名時，`resolvers` 只解析給一個，另一個「No IP for server」永遠不在線；要用 IP。
- 測試環境：同一容器跑兩個 ES，transport 綁 127.0.0.1 避開 bootstrap 檢查（跟 `e2e/local-k3s/elasticsearch-2node.yaml` 同一招）；這台測試機 ulimit 上限 20000 改不動，跨容器組 cluster 過不了 bootstrap 檢查。

**沒測到**：
- 三台 ES 的滾動重啟（推論：投票名單三台、少一台還有 master，不會有窗口）。
- k3s 上 readinessProbe 實際生效（Service 在 401 窗口不導流量）；只驗了探針指令，Secret optional 掛載的 1 分鐘延遲沒量。
- log、metrics 線（推論跟 trace 一樣，exporter 相同）。
- ECK 或雲端代管 ES 的預設探針（可能也是 elastic 帳號）。

### 量大是不是一定要 Kafka

- 佇列滿時，Collector 自己丟最舊的（`queue_size` 10,000 批），不會讓整台爆掉。
- ES 跟不上（不是停機）時回 429，Collector 退避重試，佇列慢慢堆。
- Kafka 能多給的只有「堆更久」（幾小時以上）；要先看到 ES 持續跟不上才有意義，那時該先擴 ES。
- 現在沒有這個數據。

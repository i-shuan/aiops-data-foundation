# ES 剛起來回 401，Collector 直接丟資料（2026-10）

**狀態**：已完成（repo 內的部分）　　**日期**：2026-10-24　　**相關**：分支 `claude/es-startup-401`
**模組**：① 收值（三條線送 ES 的最後一段）

## Plan：這一次要達到什麼

- **需求**：[trace-durability](2026-10-trace-durability.md) 實測 S4（ES 停機中 trace-sampler 重啟）時，看到 ES 剛起來的幾秒回 **401**，Collector 判成「帳密錯了，重試也沒用」（`Permanent error … 401`），把那幾批資料從佇列移掉。磁碟佇列、Kafka 都擋不住：擋的是「送不到」，不是「送到了被拒絕」。log、metrics 線用同一種 exporter（`otlp_http`），推論也會。
- **目的**：
  1. 搞清楚 401 **什麼時候**會出現：ES 啟動的哪一段、持續幾秒、哪種認證（API key）會遇到；ES 多台時會不會。
  2. 找到一個讓 Collector **不丟**的做法並實測：ES 還沒準備好時不要回 401（回 503 或根本連不上，Collector 都會重試）。
  3. 回答「量大是不是一定要 Kafka」：Collector 佇列滿的時候是什麼行為。
- **範圍**：只做「ES 沒準備好」這個情境。API key 真的錯、被刪掉的 401 是另一回事（那時丟掉是對的，要靠告警）。不改 ES 的部署方式（中央 ES 不在這個 repo）。

沒改 Collector：`otlp_http` exporter 把 401 當永久錯誤是對的（key 真的錯時不該無限重試），沒有「401 也重試」的選項，也不該有。

## Check：測試的目的與結果

**環境**：docker，ES 9.5.5、Collector contrib 0.162.0、HAProxy 3.1。trace 線的 trace-sampler → ES 那段（log、metrics 用同一種 exporter）。

| 測試目的（為了確認什麼） | 怎麼測 | 結果 |
|---|---|---|
| 401 在 ES 啟動的哪一段、持續多久 | 重啟 ES，每 0.1～0.3 秒同時用 API key、elastic 帳號打 GET /，記狀態碼；對照 ES log | ES 開始聽 HTTP（log `started`）起，API key **401 持續 0.9～1.3 秒**（5 次：0.88、0.92、1.3、1.9、2.7 秒），同一時間 elastic 帳號 200、`/_cluster/health` 200（status red）。401 結束的時間點 = `.security` index 的 shard 起來（RED→YELLOW）。ES log：`Authentication using apikey failed` |
| `/_cluster/health` 能不能當健康檢查 | 同上，記 health 第一次 200 的時間 | **不能**：health 回 200 的時間跟 401 開始同一秒（3 次都是） |
| 只用 elastic 帳號有沒有辦法對到「API key 能用」的時間點（`/_cluster/health/.security*?wait_for_status=yellow`） | 同上 | 差一點但不準：3 次裡 2 次同一時間，1 次 `.security` yellow 之後 API key 還 401 了 0.5 秒。**只有用 API key 自己打才準** |
| Collector 直連 ES、ES 重啟時會不會丟（重現） | S5：trace-sampler 一直在跑（磁碟佇列、正式退避 1～30 秒），t=30 重啟 ES，3,000 個 trace | 掉 0、log 沒有 401——退避剛好沒撞到那 1 秒。**撞不撞到看運氣**（trace-durability 的 S4 也是：現況撞到、A2 兩次沒撞到） |
| 把運氣拿掉：重試一定落在窗口裡 | 同 S5，重試間隔固定 1 秒（`sampler-fastretry.yaml`，只為測試） | **掉 420 個 trace**：log 10 筆 `Permanent error … 401`，`dropped_items` 共 400 段 |
| 經過「用 API key 做健康檢查」的 LB 會不會丟 | 同上（重試 1 秒），Collector 改送 HAProxy，HAProxy 用 API key 打 GET / 檢查（0.5 秒一次） | **掉 0**。Collector log 210 筆 503（HAProxy 沒有可用後端時回的），全部重試成功；HAProxy log：ES 停 → DOWN（connection refused）→ ES 起來 → 連續 2 次 200 → UP |
| 兩台 ES 只重啟一台，會不會有 401 窗口 | 同一個容器跑兩個 ES（transport 綁 127.0.0.1 避開 bootstrap 檢查，跟 `test/local-k3s/elasticsearch-2node.yaml` 同一招），kill -9 一台再起，每 0.2 秒用 API key 打那一台 | **沒有**（2 次）：連不上 → 直接 200（17.6 秒、18.1 秒）。另一台全程 200。原因：`.security` 在活著的那台，新起來的一加入就能驗 key |
| 兩台一起重啟 | kill -9 兩台再起 | **有**：先起來的那台 401 持續 1.1 秒，第二台起來時直接 200 |
| readinessProbe 的指令本身 | 對 docker 的 ES 跑三種情況：有 key 檔、key 檔是空的、key 是錯的 | 有 key → 0（Ready）；空的 → 退回 health → 0；錯的 key → 非 0（Not Ready） |

**測的過程中發現的**：

| 發現 | 怎麼發現的 |
|---|---|
| HAProxy 預設啟動時解析一次主機名；ES 容器重啟換了 IP 之後一直 DOWN，Collector 一直收 503、資料全留在佇列（沒丟，但也送不出去） | 第一次 HF 跑完 ES 裡 0 筆。加 `resolvers` 之後正常。K8s 的 Service IP 不會變，沒這個問題；LB 直接指 Pod／VM 主機名的要注意 |
| 這台測試機的 ulimit 上限 20000 改不動，兩台 ES 跨容器組 cluster 過不了 bootstrap 檢查 | 兩台起不來。改用跟 k3s 測試一樣的 loopback 繞法 |

**沒測到**：k3s 上 readinessProbe 實際生效（Service 在 401 窗口不導流量）——探針指令驗過、Secret optional 掛載的 1 分鐘延遲沒量；log、metrics 線（推論跟 trace 一樣，exporter 相同）；ECK 或雲端代管 ES 的預設探針是什麼（可能也是 elastic 帳號）。

**回答「量大是不是一定要 Kafka」**：佇列滿的行為是 Collector 自己丟最舊的（`queue_size` 10,000 批），不會「爆掉」整台。ES 跟不上時（不是停機）回 429，Collector 會退避重試、佇列慢慢堆。Kafka 能多給的只有「堆更久」（幾小時以上），這要先看到 ES 持續跟不上才有意義——那時該先擴 ES，不是加一層把問題往後延。現在沒有這個數據。

| 沒改善的 | 在什麼情況下發現的 | 影響 | 後續 |

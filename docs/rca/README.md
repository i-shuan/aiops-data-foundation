# AIOps：根因分析與動態基準線

> **類型：原理 Explanation**

根因分析只有兩步需要統計或模型：找出偏離（動態基準線學習）、從候選裡排出可能原因；串 metrics、trace、log 靠共同欄位與查詢，不靠模型。

baseline 的操作、規格、實測見 [aiops-engine/configs/baseline/](../../aiops-engine/configs/baseline/README.md)；根因分析見 [aiops-engine/configs/rca/](../../aiops-engine/configs/rca/README.md)。

## 六步與 AI 的位置

| 步驟 | 做法 | 用 AI |
|---|---|---|
| 1. 發現異常 | 每個服務、每個時段各學一份基準線，偏離就標出來 | 是：服務數百個，無法為每個設一個靜態臨界值 |
| 2. 合併告警 | 同服務、時間相連的異常合成一件（`investigator alert`） | 否 |
| 3. 定位哪一段 | 出事與平常的 trace 比較，每段只算自己的時間，差最多的排第一 | 否，統計即可 |
| 4. 找原因 | 同時間的換版（`service.version`）、資源 metrics、新出現的 log 樣式 | 是：log 歸樣式 |
| 5. 說明 | 把證據整理成文字；LLM 只能引用輸入包內的 id，引用不存在的 id 整段不顯示 | 是，只整理 |
| 6. 確認 | 人確認並回饋（[feedback/](../feedback/README.md)） | 否 |

## 三種資料怎麼串

metrics 決定何時告警，trace 指出哪一段，log 給證據。基準線用 metrics 算：每個請求都計入；應用直方圖的原始資料留 90 天（ES 8.19 的 `histogram` 不能降解析度）；trace 的 raw 只留 2 天，log 無法算分布。log 只學 `log.lines`、`log.errors` 筆數，抓 API 正常但背景工作失敗的情況。

| 鑰匙 | 路徑 | 串哪兩種 |
|---|---|---|
| 服務 | `resource.attributes.service.name` | 三種 |
| 路由 | `attributes.http.route` | metrics → trace |
| Pod | `resource.attributes.k8s.pod.name` | 三種 |
| `trace_id` | trace 與 log | trace → log |

- **metrics → trace 是統計對應**。metrics 聚合過，沒有 `trace_id`。根因分析撈同服務、同路由、同時間窗的 Server span，取最慢 200 個加出錯最多 100 個（`rca.yaml` 的 `sample`）。樣本不保證是造成異常的那個請求。
- **trace → log 是精確對應**，用 `trace_id`。
- **不用 exemplar**：ES 不存。9.5.5 與 8.19.23（經 `elasticsearch` exporter）實測都查不到 exemplar 與其 `trace_id`。
- 每段只算自己的時間：wip-worker 處理 1.5 秒、其中 1.4 秒等 Oracle，扣掉下游後只有 Oracle 那段多 1.4 秒。
- 限制：每段取平均，少數極慢請求會拉高排名；trace 100% 收，沒有取樣的遺漏。路由沒參數化時撈到 0 筆。

## 三種資料各做什麼

| 資料 | 性質 | 做什麼 | 回答 |
|---|---|---|---|
| metrics | 連續、統計 | **發現異常**：動態基準線學習、靜態臨界值規則、Pod 同儕橫向比對 | 有沒有出事、多嚴重（不知道原因） |
| trace | 事件，一個請求一筆 | **定位**：慢在哪一段、錯從哪一段開始，跟平常比 | 出在哪一段（一個請求的生命履歷） |
| log | 事件，文字 | **佐證**：用同一個 `trace.id` 撈那個請求的 log；比對出事時新出現的 log 樣式 | 發生什麼事 |

- 順序是 metrics 發現 → trace 定位 → log 佐證，三步都對**同一件**事故做一次。
- log 單獨不能定位，也算不出影響範圍，所以不是獨立的根因分析，是 trace 定位之後的佐證。

## 異常怎麼併成一件、指紋用在哪

根因分析不是每筆異常各跑一次：先把異常併成一件，再對這一件跑一次。例：mes-api 的一件含 95 筆異常，只有一份報告。

| 併件的依據 | 規則 |
|---|---|
| 服務名稱 | 同一個服務的異常歸同一件 |
| 時間相連 | 最後一筆異常離現在不到 `close_after`（30 分鐘）就併進去；超過就結束 |
| 呼叫關係 | 下游出事連帶上游異常，依 trace 裡誰呼叫誰，併一層（A→B→C 時 B 併進 C，A 不併進 C） |
| 同源只標記、不併 | 不同服務卡同一個外部依賴（同一個 Oracle）時互標 `shared_dependency`；部門、處置不同，所以不併 |

**指紋不用來併件**，用在併完、跑完根因分析之後，比對這一件跟過去已確認的 case 像不像：

| | 用在哪 | 比對什麼 |
|---|---|---|
| 併件 | 現在這批異常屬於哪一件 | 服務、時間、呼叫關係 |
| 指紋 | 這一件像過去哪一類 case | 慢的那段、錯的源頭、服務、API、log 樣式、指標；有交集就加權重，總分 ≥ 4 才算像 |

完整流程：異常 → 依服務、時間、呼叫關係併成一件 → 對這一件做 trace 定位、log 佐證 → 算這一件的指紋 → 比過去 case，以分數投票出「像哪一類」（case 只做分類，不給根因、處置）。程式在 [investigator/alerts.py](../../aiops-engine/src/incident/alert_grouper.py)（併件）、[investigator/similar.py](../../aiops-engine/src/llm/similar.py)（指紋與分類）。

## 動態基準線學習怎麼判斷

- **學**：每條序列（服務 × API × 指標），取過去 4 週同星期幾、同小時（Asia/Taipei）的中位數與 MAD，共 168 個時段。用中位數與 MAD 是因為歷史混入一次事故（例：值 500，其餘約 100）時，標準差由約 8 變約 58，中位數與 MAD 幾乎不動。
- **判**：距中位數超過 5 倍穩健標準差（1.4826 × MAD，下限為中位數的 5%），且差距大於 `min_abs`。延遲與錯誤只看變高，流量兩邊都看。
- **歷史不足時退讓**，由 `level` 欄位記錄：

| level | 基準 | 條件 |
|---|---|---|
| `dow_hour` | 同星期幾 × 同小時 | 至少 2 個不同日子（約 2 週） |
| `hour` | 每天同小時 | 至少 3 天 |
| `all` | 不分時段 | 至少 50 個點 |

  三層都不足就不判斷。
- **狀態**：超標一次是 warning；連續 2 個時間窗是 anomaly；偏離 ≥ 15 倍（`instant_z`）為單點即判定；`http.error_rate` 設 `confirm_points: 1`。
- **粒度**：每條序列在 30 秒到 1 小時自選；1 小時仍稀少的筆數類改用卜瓦松（機率 < 0.001）。
- **借用**：新 API 借同組基準線，`z: 7`；`groups` 尚未定義。
- **每天重訓**：慢速成長會被吸收。永久改變（如換版）改用 `reset_point` 從該時刻重學。
- **不改公式**：學錯時調整資料（排除時段、重學起點、放寬時段），寫入 `aiops-tuning`。

其他判斷方式：

- **靜態臨界值規則**：重啟、記憶體、磁碟等不需歷史的檢查，`rules.yaml`。
- **Pod 同儕橫向比對**：同服務 Pod 互比，`z: 5`，`peer.yaml`。10 個 Pod 壞 1 個時，服務平均仍在範圍內。
- **trace 每一段**：每個 API 學每段的呼叫次數、耗時、錯誤率；從 raw（每一段一筆、100% 收）抽樣。`trace.yaml`。

訓練資料是統計值：1 萬條序列、2～3GB，不需 GPU。門檻是歷史長度（4～8 週；年度週期要 13 個月，直方圖現在只留 90 天）與事故紀錄（幾十到幾百件）。

## 方法抓不到的

| 狀況 | 原因 | 補法 |
|---|---|---|
| 慢慢惡化（記憶體每天漲） | 基準線跟著漲 | 趨勢規則：容器記憶體照這個速度幾小時內到上限（`container.memory_leak`，✅）；其他指標的趨勢 ❌ 未做 |
| 指標之間的關係（流量正常、CPU 高） | 一次只看一個數字 | 多變量方法，❌ 未做 |
| 特殊日子（歲修、過年） | 過去 4 週沒有 | 行事曆（已做）、去年同期（需 13 個月資料） |
| 沒見過的 log 樣式、呼叫關係 | 只比數字大小 | 集合型基準線，⚠️ 僅有簡單版 |
| 天天噴錯沒人修 | 被學成「平常」 | 慢性病清單 `chronic.yaml` |

## 15 個故障案例

結論：只靠「每個服務一條數字線」抓得到不到一半；其餘需要下列做法。

| 做法 | 對應案例數 | 現況 |
|---|---|---|
| A. trace 每一段 | 6（N+1、重試風暴、冷門服務、行鎖、快取穿透、時鐘） | ✅ k3s 實測 4 個案例抓到，正常流量 0 誤報；時鐘不同步只有單元測試 |
| B. 慢請求的共同點（Pod、版本、`lot.id`、SQL） | 4 | ✅ 報告第 3 節之後：出事時那批最慢的請求 vs 平常那批，哪個值集中（[configs/rca](../../aiops-engine/configs/rca/README.md)）；只有單元測試 |
| C. Pod 同儕橫向比對 | 4 | ✅ k3s 實測錯誤率、延遲、記憶體、CPU 抓到 |
| D. metrics 補齊（p99、JVM、連線池、執行緒池、MQ lag） | 6 | ⚠️ 有流量、錯誤率、p95、CPU、記憶體；p99 ❌ |
| E. 靜態臨界值規則（飽和度） | 磁碟、連線池、GC 等 | ✅ 如 `node.disk_full`、`db.pool_exhausted` |

平均稀釋單一 Pod 與千分之一的慢請求；N+1 不動總延遲，只有次數變；慢慢爬升要看離上限多遠。JVM、連線池指標名稱隨 agent 版本而異。

### N+1 是什麼

一次就能查完的資料，被寫成查 1 次清單、再對清單裡每一筆各查 1 次。N 是清單的筆數，共 1 + N 次。

例：畫面列 3 張工單，每張要顯示批號。

| 寫法 | 查詢 | 次數 |
|---|---|---|
| 一次查完 | 給我所有工單，連同它們的批號 | 1 |
| N+1 | 給我所有工單；工單 A 的批號？工單 B 的批號？工單 C 的批號？ | 1 + 3 = 4 |

每次查詢要來回資料庫一趟，假設 2 毫秒：

| 工單數 | 一次查完 | N+1 |
|---|---|---|
| 3 | 約 2 毫秒 | 約 8 毫秒 |
| 100 | 約 2 毫秒 | 約 200 毫秒 |
| 10,000 | 約 2 毫秒 | 約 20 秒 |

- 資料少時看不出來，資料多了才變慢，所以測試正常、上線才出事。
- 每次查詢本身都快，p95 可能還在正常範圍；變的是同一個請求裡資料庫那一段的**呼叫次數**（1 次變上百次）。
- 偵測靠 trace 每一段：`trace.segment.calls` 學每段平常呼叫幾次，`trace.segment.repeated` 用固定門檻（同一個請求同一個往外呼叫 ≥ 20 次）；規格見 [baseline/reference.md](../../aiops-engine/configs/baseline/reference.md)，實測（wip-worker 每個請求查 100 次，該段 200ms，平常 33ms）見 [verification.md](../../aiops-engine/configs/baseline/verification.md)。
- 從上線第一天就有的 N+1，baseline 會學成平常，所以才要固定門檻；天天觸發沒人修的，進慢性病清單。

## 現況

- ✅ 動態基準線學習、靜態臨界值規則、Pod 同儕橫向比對、trace 每一段：k3s 驗過。
- ✅ 根因分析 Metrics → Trace → Log：`investigator` 產生報告。
- ✅ 事件整合：同服務、時間相連的異常合成一件（`investigator alert`）；跨服務依呼叫關係併一層；不同服務卡同一個外部依賴（同一個 Oracle）的件互相標同源、不合併。
- ✅ 報告有「出事前的趨勢」（突然 vs 慢慢惡化）、「慢請求的共同點」（Pod、版本、業務 ID、SQL）。
- ✅ 相似事故檢索（欄位比對）與 LLM 摘要。
- 排程：train 每天 02:00，detect、rules 每分鐘（排程器以分鐘為單位；[aiops-engine/README.md](../../aiops-engine/README.md)）。正式環境、真實資料上還沒跑。
- ⚠️ 髒資料排除（資料品質、排除時段、行事曆、慢性病）有程式、沒排程；測試流量 ❌ 無自動辨識。
- ⚠️ 真實資料的尖峰、離峰範圍需累積 2～4 週後確認。
- ❌ 事故紀錄的格式與寫入、log 樣式字典、處理手冊、單一 Pod 逐段比對。

架構與各模組狀態見 [architecture.md](../architecture.md)。

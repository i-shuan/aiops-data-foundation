# AIOps：根因分析怎麼做、哪裡需要 AI

一句話：**根因分析不是每一步都需要 AI。真正需要 AI 的是「找出不正常」和「從大量候選裡排出最可能的原因」；中間串資料的步驟，用查詢和規則就做得到。**

這份說明這個 repo 收進 ES 的 log、metrics、trace 要怎麼用來做根因分析，以及最關鍵的一件事：**怎麼知道「平常的樣子」**。

## 現況與待辦

判斷（baseline、規則、跟兄弟比、trace 每一段）和根因分析（Metrics → Trace → Log）的程式都做好了，在 k3s 驗過（程式說明：[engine/configs/baseline](../../engine/configs/baseline/README.md)、[engine/configs/rca](../../engine/configs/rca/README.md)）。上線前要補的是下面四項；告警出口、事故紀錄、回饋見 [feedback/](../feedback/README.md)。

| 項目 | 現況 |
|---|---|
| 正式環境排程 | ⚠️ 程式好了，還沒部署：train 每天、detect 每 30 秒、rules 每分鐘、peer 每分鐘 |
| [髒資料排除](#髒資料排除) | ⚠️ 偵測得到，訓練時不會排除 |
| [雜訊壓制](#雜訊壓制) | ⚠️ 已有 warning／anomaly 分級，還沒合併成同一件事故 |
| baseline 補強 | 📝 p99、慢請求比例、往外呼叫耗時；變化點偵測；只有一個 Pod 慢時拿它的 trace 逐段比；趨勢；依公司命名定義 `groups` |

### 髒資料排除

**為什麼**：系統天天噴的錯（被 catch 吞掉、沒人修），會讓 baseline 學成「每天報錯 1,000 次是常態」，真的出事反而抓不到；事故期間的資料學進去，也會把「平常」帶偏。

**現況**：✅ 偵測得到吞掉的例外、N+1、新出現的 log 樣式；✅ 中位數＋MAD，少數幾次事故影響不大。❌ 訓練時不排除事故時段；❌ 沒有「慢性病」清單；❌ 沒有資料品質檢查。

| 步驟 | 內容 | 驗收 |
|---|---|---|
| 1. 排除事故時段 | 確認過的事故（[feedback/](../feedback/README.md) 的事故紀錄）在訓練時排除；事故紀錄還沒有之前，先用「anomaly 連續超過 30 分鐘」的時段當候選、人工確認 | 插入一段事故再訓練，baseline 不被拉偏 |
| 2. 行事曆 | 歲修（一次一筆）、系統維護、大型活動：不判斷、不學；工廠 24×7 不列國定假日；年度特殊日可用去年同期（要先有 13 個月資料） | 行事曆上的時段不報、不學 |
| 3. 慢性病清單 | 每週列出「天天噴錯、沒人修」的前 10 名：吞掉的例外、固定出現的 error log 樣式、一直被限流的容器，附服務負責人 | 每週有清單；修掉的從清單消失 |
| 4. 已知問題先靜音 | 還沒修好前用 `tune` 調高門檻或固定粒度，記原因和期限 | 每筆都有原因、負責人、到期日 |
| 5. 資料品質檢查 | 序列數突然暴增（例如路由沒參數化）、必填欄位（服務名、trace.id）缺很多、某服務的資料突然停了 | 故意送沒參數化的路由會報 |
| 6. 排除測試流量 | 壓測、loadgen、測試 namespace 用 label 標出來，不學、不判斷 | 壓測期間不誤報 |

### 雜訊壓制

**為什麼**：一次 DB 變慢，同時會有好幾個 API 的延遲、錯誤率、連線池規則、跟兄弟比……30 分鐘上百筆。不收斂，值班的人很快就不看了。

**現況**：✅ 跳一次 warning、連續兩個時間窗才 anomaly；✅ 規則用 `for` 要持續一段時間，critical 一次就算；✅ 依事件數選粒度、`min_abs`；✅ 借來的 baseline 門檻較高。❌ 還沒合併成同一件事故、沒有靜音、沒有發送頻率限制。

| 步驟 | 內容 | 驗收 |
|---|---|---|
| 1. 同一條序列連續的點 → 一段 | 一段異常一筆：記開始、升級、結束；恢復要連續 N 個時間窗正常（避免在門檻邊緣反覆開關） | 一段 10 分鐘的異常只有一筆 |
| 2. 同一個服務、時間重疊 → 一件 | p95＋錯誤率＋連線池規則＋跟兄弟比 → 一件事故 | 一次 DB 變慢只有一件 |
| 3. 沿呼叫關係 → 找源頭 | 上下游同時異常的合成一件，最下游、最早開始的當源頭候選（需要常駐拓撲：每天從 trace 算一次「誰呼叫誰」存下來） | 上下游一起慢時，源頭指到最下游 |
| 4. 排優先、靜音、限頻 | critical > 影響多個服務 > 可信度高 > 持續久；行事曆時段靜音；同一件事故通知後 N 分鐘內不重發 | 每天通知數、每件事故的異常數有統計 |

**衡量**：上線前先記下現況（每天幾筆異常、多少是誤報），之後看「每天通知幾件」「一件包含幾筆異常」「誤報率」有沒有下降。

## 三種資料各回答什麼

| | 回答的問題 | 例子 |
|---|---|---|
| metrics | **有沒有出事、什麼時候開始** | 「mes-api 的回應時間從 10:05 開始變慢」 |
| trace | **一個請求經過哪些服務、哪一段造成的** | 「慢在 wip-worker 查 Oracle 那一段，從 30 毫秒變 3 秒」 |
| log | **那一段裡面發生了什麼事** | 「wip-worker 10:03 起出現 full table scan on LOT_HISTORY」 |

三種都用同一套欄位（`service.name`、`service.version`、namespace、Pod、`group`／`dept`），log 的 `trace.id` 對得到 trace 的 `trace_id`，所以串得起來。

### 分工：metrics 決定什麼時候告警，trace 和 log 說明原因

```
[過去 4 週的歷史資料]
        │
        ▼
【metrics 算 baseline】 ──────► 學出「平常週二 10:00」：
                                  • 請求量：1,200 ~ 1,500 次／秒
                                  • 延遲 p95：180 ~ 240 ms
                                  • 錯誤率：< 0.1%
                                        │
────────────────────────────────────────┼──────────────────────────
                                        ▼ 即時比對
【即時偵測：發現偏離】 ────────► 現在：延遲衝到 2,800 ms（異常）
                                        │
                                        ▼ 只調出異常那段時間
【trace 定位到哪一段】 ────────► mes-api → wip-worker → Oracle，
                                  慢在 wip-worker 查 Oracle（30 ms → 3 s）
                                        │
                                        ▼
【log 提供證據】 ──────────────► wip-worker 10:00 ~ 10:05 的 log：
                                  • 錯誤樣式：「Connection pool timeout」
                                  • 上下文：「DB host: 10.0.1.5:5432」
```

**為什麼 baseline 用 metrics 算：**

| | metrics | trace | log |
|---|---|---|---|
| 每個請求都有算到 | ✅ 應用自己記，每個請求都算 | ❌ 有取樣，調到一成就只看到一成 | ❌ 正常的請求通常不印 log |
| 延遲分布（p95、p99） | ✅ 直方圖 | ⚠️ 被取樣的那些 | ❌ 算不出來 |
| 歷史能留多久 | ✅ 可降解析度，留 1 年以上 | 7 天 | 原文 30 天 |
| 4 週算一次的成本 | 很低：已經是統計好的數字 | 高 | 中：只數筆數不讀原文還算快 |

所以 baseline 的流量、錯誤率、延遲**從 metrics 算**（應用的 `http.server.request.duration`，見 [engine/configs/baseline](../../engine/configs/baseline/README.md)）。log 只學「每個服務每個時間窗有幾筆 error」這種筆數：它能抓到 metrics 看不到的問題（例如背景工作一直失敗，但 API 都正常）。trace 和 log 原文主要在**告警之後**用：只查異常那段時間，不需要長期保留。

## 根因分析的六步

| 步驟 | 要回答的問題 | 用什麼做 | 需不需要 AI |
|---|---|---|---|
| **1. 發現異常** | 哪裡不正常？ | 每個服務、每個時段學出「平常的樣子」，偏離就標出來（見下一節） | ✅ **需要**。固定門檻在幾百個服務上不可行：每個服務的正常值不同，白天晚上也不同 |
| **2. 合併告警** | 這十個告警是不是同一件事？ | 從 trace 歸納出的呼叫關係，加上時間相近 | ⚠️ **規則為主**：有呼叫關係、同時發生就合併。AI 補沒有 trace 的部分 |
| **3. 定位到哪一段** | 慢或錯在哪個服務、哪一段？ | 比較「出事時的 trace」和「平常的 trace」，看哪一段的耗時、錯誤率變最多 | ⚠️ **統計就做得到**，AI 用來排序 |
| **4. 找出可能的原因** | 那一段為什麼變了？ | 同時間的變化：換版（`service.version`）、資源吃緊（metrics）、新出現的錯誤訊息（log） | ✅ **需要**：把幾百萬行 log 自動歸成樣式、找出突然變多的那種，要靠 AI |
| **5. 說明與建議** | 寫成人看得懂的結論 | 把證據整理成文字，對照處理手冊 | ✅ **適合用大型語言模型**，只負責整理與解釋，不負責判斷 |
| **6. 確認與回饋** | 結論對不對？ | 人確認，回饋給系統 | ❌ 人。回饋讓步驟 1、4 越來越準 |

### 例子

1. **發現異常（AI）**：mes-api 的回應時間在 10:05 偏離平常的樣子。
2. **合併告警（規則）**：mes-api、wip-worker、Oracle 同時告警；trace 顯示 mes-api → wip-worker → Oracle，合併成一件事。
3. **定位（統計）**：比對慢的 trace 和平常的 trace，wip-worker 查 Oracle 那段從 30 毫秒變 3 秒，其他段沒變。
4. **找原因**：規則找到 wip-worker 10:03 換版；AI 的 log 樣式分析發現 10:03 起新出現「full table scan on LOT_HISTORY」。
5. **說明（大型語言模型）**：「10:03 wip-worker 換版後，查 LOT_HISTORY 變成全表掃描，造成 mes-api 變慢；建議回退版本或檢查索引。」
6. **確認（人）**。

## metrics 異常怎麼串到 trace、log

用三個共同的欄位當鑰匙，依 metrics → trace → log 一路縮小範圍（[engine/configs/rca](../../engine/configs/rca/README.md)）。

| 鑰匙 | metrics | trace | log | 用途 |
|---|---|---|---|---|
| **服務名稱** | `resource.attributes.service.name` | `resource.attributes.service.name` | `resource.attributes.service.name`（alias → `service.name`） | metrics 報「哪個服務」→ 去找那個服務的 trace、log |
| **時間** | 異常的 5 分鐘時段 | span 的 `@timestamp` | log 的 `@timestamp` | 只看出事那段 |
| **路由** | `attributes.http.route`、`http.request.method`（Java 的由 Collector 改成這個名字） | span 的同名 attribute | —（REST API 解析規則做了才有） | metrics 報「哪支 API」→ 撈那條路由的 trace |
| **Pod、namespace** | `resource.attributes.k8s.pod.name` 等 | 同左 | 同左（alias → `kubernetes.pod.name`） | 規則、跟兄弟比報的是單一 Pod 時 |
| **trace_id** | — | `trace_id` | `trace_id`（alias → `trace.id`） | trace ↔ log 精確對到「同一個請求」 |

服務名稱、Pod、namespace 都是 Collector 用同一套規則補上的（不是應用自己填），三種資料一定對得上；trace_id 由自動埋點寫進 log（Java 在 MDC、.NET 在 scope；log 格式沒印出來的，用 `otel.logs.exporter: otlp` 讓 agent 直接送，見 [trace/README.md「跟 log、metrics 串起來」](../trace/README.md#跟-logmetrics-串起來)），中央 pipeline 存成 `trace.id`，alias `trace_id` 跟 trace 同名。**三種資料的鑰匙都是同一條路徑**（log 的是 alias；Java 指標名字由 Collector 改），查哪一種都不用翻譯（[pdca/2026-10-field-unify.md](../pdca/2026-10-field-unify.md)）。

### 歸屬 label 和共同鑰匙是兩種東西

兩者都是 Collector 補在資料上的，但用途不同，**不要混成一種**：

| | 歸屬 label | 共同鑰匙 |
|---|---|---|
| 用來做什麼 | 這筆資料**是誰的**：寫到哪個 data stream、誰看得到、保留幾天、告警送給誰 | 把三種資料**接起來**：從 metrics 找到 trace，再找到 log |
| 有哪些 | `dept`、`group` | 服務、路由、Pod、namespace、時間窗、`trace_id` |
| 怎麼來的 | `k8s_attributes` 讀 **namespace 的 `dept` label** → `transform/group` 依 `telemetry/groups.yaml` 算出 group；應用自己帶的 `dept`、`group` 一律先拿掉 | 服務、Pod、namespace 由 Collector 依 Pod 補；`trace_id` 由 agent 產生、自動傳遞 |
| 在哪裡 | metrics、trace：`resource.attributes.dept`、`.group`；log：`labels.dept`、`labels.group` | 見上表 |
| 異常總表 | `dept`、`group`（寫異常時補，`detector/owner.py`） | `keys` 裡 |

### 共同鑰匙圈：完整清單

| 鑰匙 | 路徑（三種資料一樣） | 目的 | 現況 |
|---|---|---|---|
| 服務 | `resource.attributes.service.name` | metrics 報哪個服務 → 去找它的 trace、log | ✅（log 用 alias） |
| 路由＋方法 | `attributes.http.route`、`attributes.http.request.method` | 哪支 API → 撈那條路由的 trace | ✅ metrics、trace；log ❌（REST 解析規則沒做） |
| Pod | `resource.attributes.k8s.pod.name` | 規則、Pod 互比報的是單一 Pod | ✅ |
| namespace | `resource.attributes.k8s.namespace.name` | 服務重名時分開；對回部門 | ✅ |
| 時間窗 | `@timestamp` | 只看出事那段 | ✅ |
| trace_id、span_id | `trace_id`、`span_id` | trace ↔ log 精確到同一個請求 | ✅（log 用 alias） |
| cluster | `resource.attributes.k8s.cluster.name` | 多個 cluster 時分開 | ✅（log 用 alias） |
| 業務 ID（交易 ID…） | 名稱未定 | 用一筆交易查全部 | ❌ 不放 metrics（每個值一條序列會爆炸），只放 trace、log |

**流程（例：mes-api 的 p95 變高）：**

```
(1) metrics：baseline 報 mes-api GET /lots/{id} 的 p95，10:05～10:20 異常
        │  帶著「服務＋時間」
        ▼
(2) trace：撈這段時間 mes-api 的請求
        出事時：最慢的 200 個＋最多 100 個出錯的（尾端取樣把這些全留了）
        平常：  一週前同一時段（沒有就用出事前同樣長的一段）
        ├ 每一段只算「自己」的時間（扣掉底下的呼叫），跟平常比，多最多的排第一
        │   → 「wip-worker 查 Oracle LOT_HISTORY 多了 1.4 秒」
        ├ 錯誤源頭：標了錯誤、底下都沒錯的那段
        └ 最慢那個請求的瀑布圖、服務之間的呼叫關係圖
        │  帶著「最慢那個請求的 trace_id」＋「可疑的服務」
        ▼
(3) log：用 trace_id 撈同一個請求在各服務的 log；可疑服務這段時間的 warn／error 歸成樣式跟平常比
        → 「新出現：Connection pool timeout waiting for connection to 10.0.1.5:5432」
        ▼
(4) 報告：哪個服務、從何時、慢在哪一段、錯誤從哪裡開始、相關的 log
```

- **為什麼要經過 trace**：慢的原因常在下游。只有 metrics 只知道「mes-api 變慢」；直接翻 log 要在幾十個服務、幾萬行裡找。trace 先縮到「哪個服務的哪一段」，log 只看那幾分鐘、那幾個服務。
- **為什麼只算自己的時間**：wip-worker 處理 1.5 秒、其中 1.4 秒在等 Oracle；不扣的話三層都看起來慢 1.5 秒。扣掉之後只有 Oracle 那段多 1.4 秒，排第一的就是源頭。

**其他偵測結果怎麼接：**

| 誰報的 | 帶什麼 | 怎麼接 trace／log |
|---|---|---|
| metrics baseline（服務、API） | 服務、API、時間 | 上面的完整流程 |
| trace 每一段的 baseline、N+1、吞掉的例外 | 服務、API、哪一段、時間 | 已經指出哪一段；再用 trace_id 撈 log |
| 規則（重啟、記憶體、連線池…） | namespace、Pod、服務（`context`）、時間 | 用服務＋時間 |
| 跟兄弟比（單一 Pod） | 服務、Pod、時間 | 目前只接到服務層級；「只拿這個 Pod 的 trace 跟其他 Pod 逐段比」在待辦 |

**目前接不起來、或接得不好的：**

1. **metrics 沒帶 trace_id**：exemplar（metrics 裡夾帶當時某個請求的 trace_id）在這個架構用不了：實測（ES 9.5.5、otelcol-contrib 0.162.0）帶 exemplar 的 OTLP metrics，直接送 ES 的 `/_otlp/v1/metrics`（正式的路線）或經 Collector 的 elasticsearch exporter（otel mode），存進去都沒有 exemplar（`_source`、mapping、全文搜尋都找不到 trace_id）。所以用「服務＋時間」代替：異常那段時間這個服務（有 API 就限定 API）的 Server span，取最慢的 200 個＋最慢的出錯的最多 100 個（`rca.yaml` 的 `sample`），瀑布圖和依 trace_id 撈 log 只用其中最慢的一個。效果接近，但不是「那一個點」的請求。
2. **.NET 的 Kafka 消費者（不改程式）**：處理訊息時的 DB、呼叫自成一個 trace，對不回訊息，只能用服務＋時間接 log（[trace/scenarios.md 場景四](../trace/scenarios.md#四非同步訊息佇列)）。
3. **單一 Pod 的異常**：上表最後一列，待辦。
4. **多個異常還不會合併成一件事**：同一個服務的錯誤率、p95、連線池同時報，現在是三筆、各跑一次根因分析。
5. **沒有 trace_id 的 log**（純文字、程式自己印的）：只能用服務＋時間撈，對不到單一請求。

## 重點：怎麼知道「平常的樣子」

步驟 1 的品質決定整個流程。判斷錯了，後面全部白做：誤報太多，大家就不看了；漏報，出事了沒人知道。

### 1. 看哪些數字

不是每個 metrics 都要學，先從每個服務的核心指標開始：

| 對象 | 指標 | 從哪裡來 |
|---|---|---|
| 每個服務的每個 API（trace 的段名稱） | **流量**（每分鐘幾個請求）、**錯誤率**、**延遲**（p50、p95、p99，不要用平均） | trace；沒有 trace 的服務用應用自己的 metrics |
| 每個 Pod、節點 | CPU、記憶體、重啟次數 | kubelet、K8s 物件狀態 |
| 每個服務的 log | 每分鐘各 level 的筆數、**各種 log 樣式的筆數** | log |

**依什麼切開來學**：`service.name` × API（段名稱）× 指標。每個組合各學一份「平常」，一個服務慢不會被別的服務平均掉。這就是為什麼三種資料的服務欄位要統一。

### 2. 「平常」會隨時間變：週期

同一個服務，白天和半夜、平日和週末、換班前後，正常值本來就不一樣。學「平常」最重要的就是學這個週期：

```
延遲 p95
  │      ┌──┐      ┌──┐                        ┌──┐
  │   ┌──┘  └──┐┌──┘  └──┐      ...         ┌──┘  └─×  ← 這個點：比上週同一時段高很多 → 異常
  │───┘        └┘        └───               ──┘
  └──────────────────────────────────────────────────── 時間
     週一          週二                        下週一
```

同樣是 800 毫秒，在尖峰時段可能是正常，在半夜就是異常。所以比的是「**這個服務、在同一個週期位置（星期幾、幾點）的過去表現**」，不是一個固定數字。

廠內特有的週期也要考慮：換班、機台定期保養（PM）、月底結帳、大量投片。已知的事件做成行事曆，學的時候標出來，那段時間不要誤判。

### 3. 方法（由簡單到複雜）

| 方法 | 怎麼做 | 優點 | 缺點 |
|---|---|---|---|
| **A. 同時段的歷史範圍** | 取過去 4 週「同一個星期幾、同一個小時」的值，算中位數與離散程度（中位數絕對偏差），超出中位數 ± 3～5 倍就算異常 | 簡單、好解釋（「比過去四週同時段高 5 倍」）、不需要訓練 | 對漸漸變化、特殊日子不敏感 |
| **B. 拆出週期再看剩下的** | 把時間序列拆成「趨勢 + 每日週期 + 每週週期 + 剩下的」，只看「剩下的」有沒有異常 | 能處理趨勢（例如流量逐月成長） | 要調參數 |
| **C. 預測模型** | 用過去的資料預測現在「應該」是多少、範圍多大，實際值超出範圍就是異常 | 準度較好、能給信心區間 | 每個組合一個模型，數量多時要管理 |
| **D. 機器學習** | 讓模型自己找週期與分布（Elastic 的異常偵測就是這類，付費功能） | 自動、可同時看多個指標 | 比較像黑盒子，要有解釋 |

**建議從 A 開始**（已實作：[engine/configs/baseline/](../../engine/configs/baseline/README.md)）：

- 不用買授權、不用訓練，ES 的查詢加上一點 Python 就做得到。
- 結果好解釋，工程師比較願意相信。
- 先上線、收集回饋，知道哪裡不夠再換 B、C 或 D。

### 4. 讓「平常」學得準的條件

| 條件 | 為什麼 | 現在的狀態 |
|---|---|---|
| **歷史夠長** | 要看到週期，至少 4 週，最好 8 週；年度週期要 13 個月 | ⚠️ 方案見 [retention.md](../retention.md)：metrics 降解析度留 400 天、log 與 trace 改留統計值 400 天 |
| **資料不缺、不重複** | 缺資料會被當成「流量掉到 0」，重複會被當成「流量暴增」，都是誤報 | ✅ 這個 repo 測過 ES 停機、當機、收集器重啟、換 key，都不掉、不重複 |
| **欄位一致** | 同一個服務在三種資料裡名稱要一樣，才切得出同一組 | ✅ `service.name`、`service.version`、`group` 三種資料一致 |
| **排除已知事件** | 學的資料裡如果混了事故、保養，「平常」會被拉偏 | ❌ 還沒有：需要事故紀錄、保養行事曆 |
| **換版後重新學** | 新版本的正常值可能不同；要分辨「新版變慢了（要告警）」和「新版本來就這樣（新的平常）」 | ⚠️ 欄位有了（`service.version`），規則還沒定 |
| **新服務** | 沒有歷史就沒有「平常」 | ❌ 還沒定：先用同類服務的範圍，或前兩週只記錄不告警 |

### 5. log 和 trace 的「平常」

- **log**：先把 log 歸成樣式（把變動的數字、ID 拿掉，例如「order * accepted」），再學「每種樣式平常每分鐘幾筆」。**新出現的樣式**和**突然變多的樣式**最有用。我們統一了 `message`、`log.level`、`error.type`，歸樣式比較準。
- **trace**：每個服務的每個 API（段名稱）學一份延遲分布。段名稱不能帶 ID（見 [sdk/standards/tracing.md](../../sdk/standards/tracing.md)），不然每個請求都是不同的名稱，學不出來。

## 不同用途要的 baseline 不一樣

> 從 15 個真實故障案例反推要哪幾種 baseline，見 [rca/cases.md](cases.md)。

上面講的（[engine/configs/baseline/](../../engine/configs/baseline/README.md) 已實作）是**「單一數字、依時段」的統計 baseline**：每條時間序列各自學「每個星期幾、每個小時，平常是多少、通常跳動多少」。它是**非監督式**的，不需要標好哪些是事故，只看歷史。

AIOps 的其他用途要的「平常」長得不一樣，有一部分可以共用這套：

| AIOps 用途 | 要回答的問題 | 要的「平常」長什麼樣 | 現在這套能不能用 |
|---|---|---|---|
| **指標異常** | 這個數字不正常嗎？ | 每條序列 × 每個時段的中位數、波動 | ✅ 就是這套 |
| **log 量異常** | 某個服務的錯誤 log 突然變多？ | 同上，數字是「每個時間窗的 log 筆數」 | ✅ 已經在學（`log.lines`、`log.errors`） |
| **log 樣式異常** | 出現以前沒見過的錯誤訊息？某種訊息突然變多？ | (1) **樣式字典**：平常會出現哪些 log 樣式（例如「order * accepted」）<br>(2) 每種樣式平常每 5 分鐘幾筆 | ⚠️ (2) 可以用這套；(1) 是另一種 baseline，要先把 log 歸成樣式、記下見過哪些 |
| **trace 延遲、錯誤** | 某個 API 變慢、錯誤變多？ | 每個服務 × API 的延遲分布、錯誤率 | ✅ 已經在學（`trace.*`） |
| **呼叫關係改變** | 出現以前沒有的呼叫？某條呼叫消失？ | **呼叫關係圖**：平常誰呼叫誰、每條線平常多少流量 | ⚠️ 每條線的流量可以用這套；「有哪些線」是另一種 baseline |
| **多個指標的關係** | CPU 變高但流量沒變？（可能是程式出問題，不是忙） | **指標之間的關係**：平常 CPU 跟流量的比例 | ❌ 這套一次看一個數字，看不出這種異常。要多變量的方法（迴歸、隔離森林之類） |
| **換版比較** | 新版本是不是變慢了？ | 依**版本**分開的分布（舊版 vs 新版） | ⚠️ 把 `service.version` 加進切分欄位就行，比較規則要另外寫 |
| **容量預測** | 再過多久硬碟、CPU 會不夠？ | **長期趨勢**（每月成長多少），不是週期 | ❌ 這套只學週期、不學趨勢。要預測模型 |
| **預測事故、自動判斷根因** | 這個模式以前是不是出過事？ | 過去的事故與當時的狀況 | ❌ 要**事故紀錄**當標註，是監督式學習 |

### 四種 baseline

1. **「數字 × 時段」**：現在這套。涵蓋指標、log 筆數、trace 延遲和錯誤，是最常用、也最先需要的一種。
2. **「集合」**：平常有哪些 log 樣式、有哪些呼叫關係。異常是「出現沒見過的」或「平常有的不見了」。
3. **「關係」**：多個指標之間平常的比例。
4. **「趨勢」與「標註」**：長期成長、過去的事故。

**共用的地基是同一套**：服務名稱、API、部門欄位一致；時間切成固定的時段；資料不缺、不重複。不管之後加哪一種，都不用回頭重整資料。

### 做的順序

| 順序 | 做什麼 | 狀態 |
|---|---|---|
| 1 | 「數字 × 時段」上線，累積資料與誤報、漏報的回饋 | ✅ 已完成（[engine/configs/baseline/](../../engine/configs/baseline/README.md)） |
| 2 | **log 樣式字典**：抓「新出現的錯誤訊息」。歸好樣式後，每種樣式的筆數直接交給第 1 項學 | 下一步 |
| 3 | **trace 呼叫關係圖**：抓新出現或消失的呼叫，也用在根因分析的「合併告警」 | |
| 4 | **多指標關係、預測事故**：要先累積事故紀錄 | 有事故紀錄之後 |

## AIOps 訓練要多少資料

一句話：**訓練用的是「統計過的時間序列」，量很小（GB 等級）；真正的門檻是「時間夠長」、「資料品質」和「事故紀錄」。** 上 TB 的原始 log、trace 是給人查問題用的，不是給模型訓練用的。

### 量：以 200 個服務、500 個 Pod 估算

| 用途 | 訓練用的資料 | 筆數 | 大小 |
|---|---|---|---|
| **發現異常**（學「平常的樣子」） | 每個服務 × API × 指標（流量、錯誤率、p95、p99）＋每個 Pod 的資源，約 **1 萬條時間序列**；每條 8 週、5 分鐘一點（約 1.6 萬點） | 約 1.6 億點 | **約 2～3GB** |
| 同上，看年度週期 | 同樣 1 萬條，13 個月、1 小時一點（約 9,500 點） | 約 1 億點 | 約 1.5GB |
| **log 樣式** | 學樣式：每個服務抽 1～7 天的 log 原文（幾十萬行就夠）；學「平常幾筆」：每個樣式每 5 分鐘的筆數，8 週 | 樣式數萬種，大多數時段是 0 | 幾 GB |
| **定位到哪一段**（trace） | 不用訓練：每個 API 的延遲分布，2～4 週（應用的 `http.server.request.duration`） | — | 包含在上面 |
| **大型語言模型做說明** | 不用訓練：當下找到的證據＋處理手冊、過去事故的文字 | — | 文字，很小 |

一台 16～32GB 記憶體的機器就訓練得動，不需要 GPU；每天或每週重新學一次。

### 真正的門檻

| 門檻 | 要多少 | 為什麼 |
|---|---|---|
| **時間長度** | 至少 4 週，最好 8 週；年度週期要 13 個月 | 要看過完整的週期（星期幾、換班、月底、保養），不然會把正常的週期當成異常 |
| **資料品質** | 不缺、不重複、欄位一致 | 缺資料會被學成「平常就會掉到 0」，之後真的掉了也不會告警 |
| **事故紀錄** | 過去的事故：發生時間、影響範圍、根因；**幾十到幾百件** | 用來驗證「找出來的異常是不是真的事故」，以及之後訓練「預測會不會出事」、「自動判斷根因」這類模型。**這是最缺的，而且只能靠時間累積** |

**所以現在最該做的不是存更多資料，而是：**

1. 照 [retention.md](../retention.md) 把長期統計值留下來（metrics 降解析度、log 與 trace 的統計），**從今天開始累積**。
2. **開始記錄事故**：每次出事記下開始和結束時間、影響哪些服務、根因是什麼。格式簡單就好，重點是持續記。幾個月後就是 AIOps 最有價值的訓練資料。

## 建議順序

1. **步驟 1**：用方法 A 對每個服務的核心指標做異常偵測。整個流程的起點，最快看到效果。
2. **步驟 3**：用 trace 定位到哪一段。純統計，效果明顯。✅ 已做：[engine/configs/rca](../../engine/configs/rca/README.md) 從 baseline 的異常開始，照 Metrics → Trace → Log 查一遍，產出報告。
3. **步驟 4 的 log 樣式分析**：AI 最有價值的地方，能抓到人工翻 log 找不到的「新錯誤」。
4. **最後加大型語言模型做說明**：前面的證據越完整，它寫的結論越可靠。

步驟 1、4 的 AI 可以自己做（Python 從 ES 讀資料），也可以用 Elastic 的付費功能（異常偵測、log 樣式分群、log 量突變分析；免費授權實測都不能用，見 README 待辦）。

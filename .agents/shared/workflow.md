# workflow — 需求流程

每個需求一個資料夾，用**英文 kebab-case** 命名。範本在
[`requirements/_template/`](../../requirements/_template)。

```
requirements/<english-kebab-name>/
├── 1-intent.md       為什麼要做、解決誰的什麼問題、**不做什麼**
├── 2-spec.md         要做成什麼樣、影響到哪些既有行為
├── 3-plan.md         怎麼做、會動到哪些檔案、風險與退路
└── 4-acceptance.md   怎麼算完成 —— 可執行的指令加預期輸出
```

| 規則 | |
| --- | --- |
| 一次只往前一個階段 | 寫完 `1-intent.md` 要人確認才寫 `2-spec.md`。一口氣四份的結果是 intent 還沒談定，plan 已經假設了一堆沒講好的事 |
| 沒有 `4-acceptance.md` 不算完成 | 驗收項要是**可執行的指令加預期輸出**，不是「功能正常」 |
| `3-plan.md` 檔案清單 > 3 就停 | 拆成多個需求 |
| 中途改方向要同步改 `2-spec.md` | 不然文件和實作分家 |

⚠️ 檔名用 `1-intent.md` 不是 `1. intent.md`。檔名有空格的話 `cd`、`cat`、
`git add` 都要加引號，而示範指令被照貼進終端機時會壞掉。

## 變更流程（每次任務）

1. **定位範圍** —— 動手前輸出預計變動的檔案清單（≤ 3 個），不要無目的 `cat` 全文
2. **實作** —— 最小變更
3. **針對性驗證** —— 只跑該模組的測試或型別檢查；改了文件要跑 `check-md-style.py`
4. **收尾三段式**（禁止客套詞）：
   * **改動摘要**：變更的檔案與核心邏輯
   * **驗證結果**：執行的指令及其**實際輸出**
   * **潛在風險**：無法在本地驗證的事項（無則填「無」）
